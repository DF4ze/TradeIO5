## Entités (schéma créé par `ddl-auto=update` ; migration Flyway préparée mais non activée, cf. [`../operations/flyway.md`](../operations/flyway.md))

- `RainbowLivePreset` (`rainbow_live_preset`) : `user` (FK `User`), `assetSymbol` (BTC|ETH|PAXG), `name`, `enabled`, `analysisWindowMonths`, `initialCapitalUsdc`, `assetStrategy` (FK nullable vers `RainbowAssetStrategy`, colonne `asset_strategy_id` : le preset **suit** la stratégie Actif ⇒ non modifiable, non supprimable, config lue dans la stratégie à chaque passe ; nul = preset propre au user), `createdAt`/`updatedAt`, + `@Embedded RainbowAtrConfig`. **Unique (user, asset_symbol, name)**. Timeframe 1D fixe (non stocké).
- `RainbowAtrConfig` (`@Embeddable`) : 1 colonne typée par paramètre = `RainbowAtrTuning` (17) + `RainbowAtrGlobals` (12 + `multX2/X1/X0_5/Triggered` + `baseAmount`). `of(tuning, globals)`, `toTuning()`, `toGlobals()`, `hash()` (SHA-256 tronqué). `baseAmount` n'existe que dans la config (pas de colonne en double sur le preset). Réutilisé tel quel (mêmes noms de colonnes) comme snapshot dans le run.
- `RainbowAssetStrategy` (`rainbow_asset_strategy`) — **Stratégie Actif**, pilotée par le compte System : une par actif (« TrendMix Rainbow DCA ATR · BTC|ETH|PAXG »), sans user, wallet ni run : `assetSymbol`, `name`, `mode`, `analysisWindowMonths`, `initialCapitalUsdc`, `@Embedded RainbowAtrConfig` (instantané du jeu Bear), `trendConfigJson` (`TrendConfigDto` sérialisé, null si FIXED), `revision` (1 à la création, +1 à chaque modification), `createdAt`/`updatedAt`. **Unique (asset_symbol, name)**. Modifiable (`RainbowAssetStrategyService#update`, endpoint admin), jamais supprimable (`@PreRemove` lève une exception). Créée par `RainbowAssetStrategyInitializer` si absente, **jamais écrasée** ; le catalogue du code (`RainbowAssetStrategyService#catalog`) ne sert que de graine. Seules les stratégies TrendMix sont fournies : les « Bench global » FIXED ne sont plus suivables (un user peut en créer à la main).
- `RainbowLivePresetEvent` (`rainbow_live_preset_event`) : historique des switchs de preset d'un user (`type` ENABLE | DISABLE | DETACH | LIVE_SWITCH | STRATEGY_CHANGED, `assetSymbol`, id + nom du preset avant/après sans FK, `strategyRevision`, `occurredAt` via `DomainClock`, `reason`), `ON DELETE CASCADE` sur le user. Écrit par `RainbowLivePresetEventService` : activation/désactivation effective (`setEnabled` qui change la valeur), détachement (voir ci-dessous), création/bascule d'un binding (`LIVE_SWITCH`, avant nul à la création), et `STRATEGY_CHANGED` à la 1re passe qui constate une nouvelle révision (une fois par preset et révision).
- `RainbowLivePreset.mode` (`RainbowLiveMode`, nullable = `FIXED`) : `FIXED` (un jeu de paramètres, rejeu de la fenêtre à chaque passe) ou `TREND_MIX` (jeu Bull/Bear choisi chaque jour par la Trend Mix, état persisté). `RainbowLivePassBlock` porte aussi `activeSet` (ex. « BTC Perso Bull ») et `trendRegime` (UP/DOWN/RANGE), exposés par l'API (`BlockDto`, `PresetDto.mode`).
- `RainbowLiveTrendConfig` (`rainbow_live_trend_config`) : 1-1 avec un preset `TREND_MIX` (`ON DELETE CASCADE`) : paramètres du Trend Mix (colonnes typées), `rangeMapping` (`KEEP_PREVIOUS|TO_BEAR|TO_BULL`) et les jeux Bear/Bull (`bearJson`/`bullJson` = `{tuning, globals}`). Absente ⇒ défauts du code (`RainbowLiveTrendConfigs#defaults`).
- `RainbowLiveUserSettings` (`rainbow_live_user_settings`) : une ligne par user, `uiMode` (`RainbowLiveUiMode` AUTO|SIMPLE|ADVANCED|EXPERT ; absente ⇒ `EXPERT`).
- `RainbowLiveEngineState` (`rainbow_live_engine_state`) : unique (preset, `state_day`), `ON DELETE CASCADE` ; état de la machine Rainbow (`RainbowAtrState` : armements, verrou, cooldown, réserve moon, automate moon) + `configHash` (empreinte de la config effective : fenêtre + jeux Bear/Bull + réglages Trend, ou jeu FIXED) à la FIN du jour, après la passe 23:55. NaN stockés `null`.
- `RainbowAthReference` (`rainbow_ath_reference`) : unique (actif, `ref_day`) ; ATH par ACTIF valable à la fin du jour (une ligne par jour, pour que la passe 00:05 relise l'ATH de la veille).
- `RainbowLiveMockWallet` (`rainbow_live_mock_wallet`) : 1-1 avec le preset (`ON DELETE CASCADE`), `cashUsd`, `positionQuantity`, `assetSymbol`. Implémente `PortfolioView` (`cash()` en USD, `quantity(asset)`) — interface fine, ne présuppose pas « 1 wallet = 1 actif ». `applyBuy` refuse un achat > cash, `applySell` une vente > position. Distinct de l'entité `Wallet` (exchange) ; seul stablecoin : USDC.
- `RainbowLiveBinding` (`rainbow_live_binding`) : lien (user, actif) → **preset live** + **wallet réel** (lecture seule). **Unique (`user_id`, `asset_symbol`)** (pas d'index partiel : MariaDB) ⇒ un seul preset live par actif, imposé en base. Champs : `preset` (FK, doit appartenir au user et à l'actif), `wallet` (FK `Wallet`, doit appartenir au user), `bagPercent` (0-100, défaut 100, part **dynamique** de la position réelle offerte à la stratégie), `priority` (ordre de passage du cash, défaut = rang dans `RainbowLiveDefaultPresets.ASSETS` : BTC 0, ETH 1, PAXG 2). Bascule du live = modification du binding (l'ancien preset n'est plus lié : simulation, historique conservé) ; un preset lié ne peut pas être supprimé (400). Donnée utilisateur créée par l'API, jamais par un initializer. Lu par le moteur via `RealPortfolioSource` (cf. « Preset live sur vrai cash »).
- `RainbowLiveRun` (`rainbow_live_run`) : **unique (preset, `run_day`)**, `ON DELETE CASCADE` sur le preset ; `user`, `assetSymbol`, `day` (jour UTC), deux blocs `@Embedded` `RainbowLivePassBlock` nullables indépendamment (`pass2355` → colonnes `t2355_*`, `pass0005` → `t0005_*`), `config` (snapshot) + `configHash`. `deltaActionDiffers()` : vrai si les deux blocs existent et que type/montant/quantité d'action diffèrent.
- `RainbowLivePassBlock` : `close`, `sma`, `atr`, `boundDown2`/`boundDown1`/`boundUp1`/`boundUp2`/`boundUp3` (SMA ± ATR×mult correspondant, extrêmes DOWN2/UP3 compris), `zone`, `athDistance`, `buyFactor`/`sellFactor`, `moonMode`, `buyArmed`/`sellArmed`/`buyLocked`, `cooldownRemaining`, `moonReserveQty`, action (`RainbowLiveAction` BUY/SELL/NONE, `actionAmountUsdc`, `actionQuantity`, `actionPrice`), `cashAfter`/`positionAfter`, `configHash`, `computedAt`.

Suppression d'un preset ⇒ wallet mock + runs supprimés par FK. Édition d'un preset ⇒ même id, wallet et historique conservés, aucun run écrit ni recalculé.

## Sémantique des deux passes (`RainbowLiveRunService#upsertPass`)

Idempotent par (preset, jour, passe) ; horloge `DomainClock` (`computedAt`).
- **23:55** : action fictive. Appliquée au wallet mock **une seule fois par (preset, jour)** ; `cashAfter`/`positionAfter` renseignés par le service. Rejeu : indicateurs remplacés, mais action et état du wallet d'origine conservés.
- **00:05** : mêmes indicateurs sur la vraie clôture + « action qui aurait été prise », **jamais appliquée** (n'altère ni le bloc 23:55 ni le wallet). Peut exister sans 23:55.
- Chaque upsert rafraîchit le snapshot de config du run et le hash (aussi stocké dans le bloc) ; comparer au hash du preset détecte « config modifiée ».
- Un achat supérieur au cash lève `IllegalStateException` (rien n'est persisté) : l'appelant (`RainbowLiveExecutionService`) plafonne donc AVANT l'appel.

## Presets (`RainbowLivePresetService`)

`create` (valide `Tuning.isValid()`, fenêtre ≥ 1, capital > 0, baseAmount > 0, actif autorisé, nom libre ; crée le wallet mock à `initialCapitalUsdc`), `update` (nom, enabled, fenêtre, config ; actif et capital non modifiables), `delete`, `get(user, id)`, `list(user[, actif])` ; opérations réservées au propriétaire. Erreurs typées (sous-classes d'`IllegalArgumentException`) : `RainbowLivePresetNotFoundException` (inexistant **ou** d'un autre user), `RainbowLivePresetConflictException` (nom déjà pris pour l'actif).

**Stratégie Actif et presets qui la suivent** : `RainbowAssetStrategyInitializer` (`@Order(60)`, au démarrage) insère les stratégies absentes du catalogue (une « Trend Mix » par actif, réglages par défaut du code) et ne modifie jamais une stratégie existante ; System la modifie ensuite en base (`PUT /api/admin/rainbow-live/strategies/{id}`, fenêtre + réglages Trend dont jeux Bear/Bull, validations de `RainbowLiveTrendConfigs#normalize` ; `revision` + 1). `ensureStrategyPresets(User)` (appelé par la passe quotidienne et par `GET /presets`) crée, pour chaque stratégie dont le user n'a pas le preset, un preset qui la **suit** : nom = `SYSTEM_PREFIX` (« [Système] ») + nom de la stratégie, `assetStrategy` renseignée, **inactif** (`enabled=false`), wallet mock au capital de la stratégie, runs propres, **aucune copie de config ni ligne Trend**. Jamais recréé ni modifié. Sur un preset qui suit, `update` et `delete` lèvent `RainbowLivePresetFollowsStrategyException` (409) ; seul `setEnabled` (`PATCH /presets/{id}/enabled`) est permis. Le préfixe est réservé : refusé (400) sur un preset créé ou renommé par l'utilisateur.

**Config effective** (`RainbowLivePresetConfigResolver`) : accesseur unique de la config d'un preset (`config`, `analysisWindowMonths`, `trendConfig`, `effectiveHash`) = celle de la stratégie suivie (lue à chaque appel) ou, pour un preset propre, ses colonnes / sa ligne `RainbowLiveTrendConfig`. Lecteurs : `RainbowLiveExecutionService` (FIXED), `RainbowTrendLiveService`, `RainbowLiveRunService` (snapshot du run), `RainbowLiveQueryService` (DTO). Un changement de la stratégie s'applique donc à la passe suivante chez tous les users qui la suivent, sans toucher aux détachés.

**Détachement** : dupliquer un preset qui suit une stratégie (`POST /presets` avec `duplicatedFromId`) crée un preset propre (`assetStrategy` nulle, réglages copiés dans sa propre ligne, nouveau wallet mock) ; l'ancien preset garde son wallet, ses runs et son état. Événement `DETACH` (révision suivie). La page affiche un avertissement avant la duplication d'un preset qui suit : plus de mises à jour de System.

## Exécution quotidienne (`RainbowLiveExecutionService#runPass(pass, asOf[, dayOverride])`)

Horloge injectée (`DomainClock` dans les jobs/l'endpoint, `asOf` explicite en test) ; `synchronized` (cron et déclenchement manuel ne se chevauchent pas).

- **Jour UTC traité** (`dayFor`) : `T2355` ⇒ date UTC de `asOf` ; `T0005` ⇒ date UTC de `asOf` − 1 (la clôture qui vient de se terminer). `dayOverride` (endpoint) force le jour.
- **Utilisateurs/presets** : pour chaque `User` `enabled` non archivé, `ensureStrategyPresets` puis presets `enabled` groupés par actif. Clé user jamais codée en dur. Une erreur (user, actif, preset) est comptée et n'arrête jamais les autres ; pas de rattrapage des jours manqués.
- **Données** : `MarketDatasetEngine.getDatasetForAsset(actif, D1, D1_LOOKBACK_CANDLES, asOf)` (pipeline officiel + fallback `asset_provider`), chargé **une fois par (actif, passe)** et partagé entre presets/users (un seul `RainbowAtrDataset`, caches SMA/ATR partagés). La bougie du `day` est repérée par sa date UTC ; la bougie du jour suivant (présente à 00:05) est ignorée ; bougie absente ⇒ WARN, actif sauté (pas d'exception). Dataset < warmup+2 ⇒ preset sauté.
- **Contrainte bucket** : D1 est un resampling de H1 (`Bucket`, `BASE_MAX_ITEMS` = 100 000 H1 ≈ 4166 j). `RainbowLiveDefaultPresets.D1_LOOKBACK_CANDLES` = 4000 (4000 × 24 = 96 000 H1) couvre BTC/ETH depuis 2017-08 sans dépasser la capacité (test de garde sur la taille). La dernière bougie D1 est l'agrégat H1 potentiellement incomplet (voulu pour 23:55). Le bucket est en mémoire (singleton) : 1er appel lourd, puis refetch incrémental à chaque nouvelle bougie H1 (cf. [`04-market-data.md`](04-market-data.md#bucket-en-mémoire-marketdatasetengine--manager--bucket)) ; perdu au redémarrage.
- **Rejeu** : `startIdx = max(warmup(sma, atr), 1re bougie ≥ day − analysisWindowMonths)`, `endIdx` = bougie du jour ; `RainbowAtrEngine.simulate(..., trace=true)` (moteur inchangé). ATH/moon sur tout l'historique chargé.
- **Action du jour** = events dont `index == endIdx` : `BUY_ZONE`/`BUY_TRIGGERED` ⇒ BUY (montant moteur en USDC), `SELL`/`MOON_STOP` ⇒ SELL (quantités sommées). Achat et vente sur la même bougie (ex. `MOON_STOP` sans cooldown) : la **vente l'emporte** (WARN).
- **Dimensionnement (dans le service, pas dans le moteur)** : achat `min(montant, cash mock)` (cash 0 ⇒ `NONE`), quantité = montant / close ; vente `min(quantité, position mock)` (position 0 ⇒ `NONE`), produit = quantité × close. À 00:05 : même calcul sur l'état courant du wallet (non modifié ; `upsertPass` n'applique jamais l'action 00:05).
- **Limite connue assumée** : le rejeu repart d'une position moteur nulle, le wallet mock est la vérité cumulée ; moteur et wallet divergent donc (le moteur peut vouloir vendre plus que le mock ne détient). Le wallet ne sert qu'à plafonner.
- **Persistance** : bloc `RainbowLivePassBlock` complet (close, sma, atr, 5 bornes, zone, facteurs ATH, états des machines, `moonReserveQty`, action, `actionPrice` = close) via `upsertPass`. Retour : `PassSummary(pass, day, processed, skipped, errors)`.

## Presets `TREND_MIX` (`RainbowTrendLiveService`)

Même wallet mock, mêmes runs, mêmes jobs et mêmes deux passes que le mode `FIXED`. Pour un preset `TREND_MIX`, `RainbowLiveExecutionService` délègue à `RainbowTrendLiveService#run` :

1. **Trend** : `TrendMixCalculator` (réglages du preset, cf. [`09-trend.md`](09-trend.md)) sur le dataset D1 chargé, puis `RainbowSetSelector` (RANGE selon `rangeMapping` du preset, Bear au départ) → jeu Bear/Bull du preset (`RainbowLiveTrendConfigs#resolve` : ligne `RainbowLiveTrendConfig`, sinon `RainbowAtrPresets.bearBull`). Le montant de base est celui du jeu actif (`globals.baseAmount`). Les runs écrits restent figés (snapshot de config + `configHash` par run).
2. **État** : dernière ligne `RainbowLiveEngineState` antérieure au jour **si son `configHash` == `RainbowLivePresetConfigResolver#effectiveHash`** (fenêtre + jeux Bear/Bull + réglages Trend). Absente (1re passe) ou hash différent (réglage propre modifié, révision de la stratégie suivie) ⇒ (ré-)amorçage par `RainbowAtrReplay.runFull` sur `analysisWindowMonths` mois jusqu'à la veille avec la config courante (pas de rejeu mixte ancien/nouveau). Le ré-amorçage est enregistré à la passe 23:55 (la ligne de la veille est réécrite avec le nouveau hash) ; la passe 00:05 d'un changement de config le calcule en mémoire sans rien écrire. Un ré-amorçage d'un preset qui suit écrit `STRATEGY_CHANGED` (une fois par preset et révision). Hors changement, l'état est recalculé à chaque 23:55 depuis celui de la veille (un seul `RainbowAtrStrategy#step`), jamais rejoué sur toute la fenêtre.
3. **ATH** : `RainbowAthService#athBefore` (ATH de la veille, lu en base). Amorçage one-shot à la 1re demande d'un actif sans aucune ligne : historique D1 complet Binance (`BinanceDailyCandleFetcher`, klines publics, seul appel exchange du bench, une fois par actif), puis une ligne par jour écrite par la passe 23:55.
4. **Dimensionnement** : `ReferenceSizer` (base × facteur ATH × multiplicateur de zone ; vente = fraction × position), plafonné par le wallet mock (achat ≤ cash, vente ≤ position ; achat et vente le même jour : la vente l'emporte).
5. **Écritures** : l'état du jour et l'ATH du jour ne sont écrits qu'à la passe 23:55, après l'enregistrement du run (`Outcome#commit`). La passe 00:05 recalcule sur la vraie clôture à partir de l'état de la veille (cash/position reconstitués en retirant l'action 23:55 déjà appliquée) et n'écrit ni état ni ATH. Rejouer une passe est idempotent.

Limite connue : l'état amorcé par rejeu repose sur une position virtuelle, le wallet mock est la vérité cumulée (comme en mode `FIXED`).

Création / édition : `POST /presets` avec `mode=TREND_MIX` + `trendConfig` (parties absentes ⇒ défauts de l'actif), `PUT` avec `trendConfig` (absent ⇒ inchangé) ; validation `RainbowLiveTrendConfigs#validate` (fenêtres ≥ 2, `0 ≤ exit ≤ enter`, `confirm ≥ 1`, tunings valides, `baseAmount > 0`). La config embarquée du preset recopie le jeu Bear (instantané informatif).

Les presets Trend Mix par défaut sont les stratégies Actif « Trend Mix » (cf. §Presets) ; plus de propriété de semis.

## API REST utilisateur (`RainbowLiveController`, `/api/rainbow-live`)

Contrat détaillé : [`../api/rest-endpoints.md`](../api/rest-endpoints.md). `@PreAuthorize("isAuthenticated()")` au niveau classe ; utilisateur = `IAuthenticationFacade#getConnectedUser()` ; tout est scopé à l'user connecté (aucune clé user en dur), preset d'un autre user ou inexistant ⇒ 404. DTO dédiés (`RainbowLiveDtos`, jamais d'entité JPA) ; `tuning`/`globals` = records `RainbowAtrTuning`/`RainbowAtrGlobals` tels quels. Erreurs : `RainbowLiveControllerAdvice` (limité à ce contrôleur) ⇒ `IllegalArgumentException` 400, not found 404, conflit de nom 409. Lectures via `RainbowLiveQueryService` (`@Transactional(readOnly)`, requêtes bornées par plage de jours, agrégats presets en 3 requêtes groupées) ; `listPresets` est en écriture (copie des templates système).

- **`configChanged` / `changedParams`** : par run, `configChanged` = `configHash` ≠ celui du run précédent du preset (le 1er run d'une plage `from` est comparé au run antérieur hors plage ; le tout premier run ⇒ `false`) ; `changedParams` = `RainbowAtrConfig#diff` des snapshots (noms des composants de `RainbowAtrTuning` nus, de `RainbowAtrGlobals` préfixés `globals.`, ex. `smaPeriod`, `globals.athRefDdBuyPct`). Même liste de marqueurs dans `/performance` (`configMarkers`).
- **Performance** (`RainbowLivePerformanceCalculator`, pur, à la lecture, rien de persisté) : rejeu des actions figées des blocs 23:55 du 1er run jusqu'à `to`. BUY ⇒ investi/position/coût de revient ; SELL ⇒ réalisé += produit − coût × qté/position (coût moyen). Mêmes définitions que `RainbowAtrResult`/pine : restant = position × dernier close, potentiel = restant − coût, total = vendu + restant − investi, pourcentages rapportés à l'investi (0 si investi = 0, jamais de NaN/Inf). Un jour sans bloc 23:55 est ignoré (pas de rattrapage). Reflète le **wallet mock** (actions plafonnées), pas la position du rejeu moteur (cf. limite ci-dessus) ; une vente > position est plafonnée à la position.
- **DCA fixe de référence** : à chaque jour ayant un bloc 23:55, achat de `baseAmount` (celui du snapshot de config du run du jour) au close du jour, à partir du 1er run ; jours manquants non comblés ; valorisé au dernier close. `outperformanceGain` / `outperformancePoints` = stratégie − DCA fixe (gain, points de PnL %).
- **Équité wallet mock** : `cashAfter + positionAfter × close` stockés par le 23:55 du dernier jour, vs `initialCapitalUsdc` ; la position rejouée == `positionAfter` stocké (testé).
- **Delta** (`RainbowLiveDeltaCalculator`) : jours ayant les deux blocs ; nb de jours où l'action diffère (détail 23:55 vs 00:05), écarts moyens/max absolus et en % de la valeur 23:55 sur close, sma, atr et les 5 bornes, divergences de zone et d'états des machines (`moonMode`, `buyArmed`, `sellArmed`, `buyLocked`, `cooldownRemaining`).

## Bindings et vérification de disponibilité (`service/dca/atr/binding/`)

- `RainbowLiveBindingService` : CRUD scopé au user (binding, preset ou wallet d'un autre user ⇒ `RainbowLiveBindingNotFoundException`/`RainbowLivePresetNotFoundException` ⇒ 404 ; binding déjà existant pour l'actif ⇒ 409 ; mauvais actif de preset, `bagPercent` hors [0,100], actif inconnu ⇒ 400). Création et modification retournent le résultat de `BindingCheck` sans le persister : un KO n'empêche pas l'enregistrement.
- `BindingCheck` (appelable depuis le moteur) → `BindingCheckResult(status, message, quoteMember, bridgePair)` (`isOk()` = OK ou VIA_BRIDGE : lecture autorisée ; `isExecutable()` = OK seul ; `isBlocked()` = NOT_TRADABLE_WITHOUT_FIAT), jamais d'exception métier. Ordre : wallet activé (`WALLET_DISABLED`) → credential active (`CREDENTIAL_INVALID`) → lecteur + vérificateur pour l'exchange (`PROVIDER_UNSUPPORTED`) → lecture des soldes via `ReadOnlyBalanceReader` (`CredentialRejectedException` = clé/signature/passphrase/permission/IP rejetées ⇒ `CREDENTIAL_INVALID` ; autre panne ⇒ `BALANCE_UNAVAILABLE`) → chemin spot **sans monnaie fiat** (membres du groupe `USD` par `position`, catalogue en base) : paire `<actif>/<membre préféré>` ⇒ `OK` ; sinon `<actif>/<autre membre>` **et** passerelle `<préféré>/<autre membre>` ⇒ `TRADABLE_VIA_BRIDGE` (`quoteMember`, `bridgePair` renseignés) ; sinon `NOT_TRADABLE_WITHOUT_FIAT` (ex. PAXG sur Kraken) ; catalogue absent et exchange injoignable ⇒ `INSTRUMENT_UNAVAILABLE`. Solde nul accepté, clé absente de la map = solde 0 (pas indisponible) ; les soldes ne sont ni conservés ni exposés.
- **Catalogue d'instruments** (`service/market/instrument/InstrumentCatalog`, table `exchange_instrument` : provider, `inst_id` `BASE-QUOTE` normalisé, base, quote, `state`, `min_sz`, `lot_sz`, `tick_sz`, `fetched_at`, unique (provider, inst_id)) : lu par `BindingCheck` et `PathFinder`. Alimenté par **un seul** appel public « toutes les paires » par exchange via `InstrumentListClient` (`OkxInstrumentListClient` : `GET /api/v5/public/instruments?instType=SPOT`, `state=live` ; `KrakenInstrumentListClient` : `GET /0/public/AssetPairs`, noms normalisés par `KrakenAssetNames`, `status=online`, paires `.d` ignorées). Rafraîchi à la demande quand il a plus de 24 h (`tradeio.execution.instrument-catalog.refresh-after`, défaut `PT24H`) ou via `refresh(provider)` ; panne ⇒ catalogue conservé (WARN), jamais vidé, pas de nouvelle tentative avant 5 min ; catalogue absent et exchange injoignable ⇒ `InstrumentLookupException` ⇒ `INSTRUMENT_UNAVAILABLE`. Plus aucun appel `instruments` unitaire par `check()`. Pas de checker Binance (pas de wallet Binance).
- `WalletInitializer` ne crée plus de wallet Binance ; il crée le wallet « OKX » (credential OKX si présente) en plus de Kraken/Binance Test/Ledger. Les lignes déjà en base ne sont pas touchées.
- `RainbowLiveNoExchangeDependencyTest` : voir « Preset live sur vrai cash ».

## Chemin d'achat chiffré : frais, carnet, PathFinder, Fee Test (lecture seule, aucun ordre)

Calcul **à la demande** (`GET /api/rainbow-live/bindings/{id}/path-quote?amount=`, cf. [`../api/rest-endpoints.md`](../api/rest-endpoints.md)) ; aucun job, aucune écriture hors cache du catalogue. `BindingPathQuoteService` (`service/dca/atr/binding`) : binding du user (sinon 404) → soldes du wallet (`ReadOnlyBalanceReader`) filtrés sur les membres du groupe `USD` (sources) → catalogue → `PathFinder` avec un marché réel (`LegMarketSource`).
- **Frais réels** : `TradingFeeProvider` / `OkxTradingFeeProvider` (`GET /api/v5/account/trade-fee?instType=SPOT&instId=…`, clé Read du wallet, signature HMAC partagée avec `OkxBalanceReader` dans `OkxSignedRequests`). Taux OKX signés (négatif = frais payé) normalisés en `FeeRate(makerPct, takerPct)` en % (positif = coût) ; champs `maker/taker` pour les paires USDT, `makerUSDC/takerUSDC` pour les paires USDC ; champ absent ⇒ `BalanceUnavailableException` (jamais de frais supposé). Cache mémoire 24 h sur `DomainClock` (échecs non cachés), throttle 500 ms entre appels réseau. Compte OKX de Clem (EEA, niveau « Utilisateur régulier ») : 0,10 % maker / 0,20 % taker, 0 % sur `USDC-USDT` ; `takerUSDC` lu pour les paires USDC (devis réels `PAXG` via USDC→USDT→PAXG et `BTC-USDC` validés). Le coût d'une jambe utilise le taux **taker** (ordres limit IOC prévus). Clé rejetée (50100-50114) ⇒ `CredentialRejectedException`.
- **Carnet public** : `OrderBookClient` / `OkxOrderBookClient` (`GET /api/v5/market/books?instId=&sz=50` → `OrderBookSnapshot`) ; repli `GET /api/v5/market/ticker` (un niveau par côté) marqué `estimation=TICKER` (slippage non chiffré). Un appel par devis, pas de cache. Kraken : tout appel par paire doit convertir les symboles standard vers les noms Kraken (BTC→XBT, via `KrakenApiClient.normalizeAsset`) ; le catalogue, lui, expose des `inst_id` en symboles standard (`KrakenAssetNames`). Ni frais ni carnet (devis `PathQuoteUnavailableException` si un chemin existe ; `NO_PATH` reste calculé).
- **`PathFinder`** (`service/market/instrument`, pur) : arêtes BUY `QUOTE→BASE` (ask) et SELL `BASE→QUOTE` (bid) pour chaque paire du catalogue ; paires touchant un nœud interdit ignorées (fiat : `ExecutionDefaults.FIAT_CURRENCIES`, surcharge `tradeio.execution.forbidden-nodes`, liste CSV) ; sources = devises détenues ; profondeur ≤ `ExecutionDefaults.MAX_PATH_DEPTH` (2), énumération exhaustive (minimum exact, sûr avec rebate négatif). Coût d'une jambe = frais + demi-spread `(ask−bid)/(ask+bid)` + slippage au montant (VWAP du carnet, `BookSlippage`) ; chemin = **somme brute**. Seules les paires **cotées en stable** (membres du groupe `USD`) sont valorisées ; chaque jambe est valorisée au même montant nominal USD. `sz` : ⌊⌋ au `lotSz` en BUY, ⌈⌉ en SELL, `minSz` ⇒ `BELOW_MIN` ; prix de référence arrondi au tick (BUY ↑, SELL ↓). Le devis est toujours dimensionné sur `amount` (taille de l'achat alloué au bag), jamais sur le cash disponible : les soldes ne servent qu'à choisir la source (suffisante préférée) et à lever `underfunded=true` si aucune ne couvre `amount`. Option `preferredQuote` (ex. `USDT`) : si un chemin finit par cet achat, seuls ceux-là sont retenus ; non fournie ⇒ coût minimal pur. Résultat `PathQuote(status OK|NO_PATH|BELOW_MIN, source, legs[], totalCostPct, feeTestLevel, estimation BOOK|TICKER, underfunded)` ; `NO_PATH` ⇒ « non tradable sans monnaie fiat » (ex. PAXG sur Kraken).
- **`FeeTest`** (pur) : coût total < `warn-pct` ⇒ GREEN ; de `warn` à `red` **inclus** ⇒ WARNING ; > `red` ⇒ RED. Propriétés `tradeio.execution.fee-test.warn-pct` (défaut 0,2) et `red-pct` (0,8), défauts en constantes (`ExecutionDefaults`). Pourcentages exposés en %, jamais en bps.
- Gardes : `ConnectorNoOrderMethodTest` et `RainbowLiveNoExchangeDependencyTest` inchangés ; aucune méthode d'ordre.

## Groupes d'actifs (USD = USDC + USDT)

## Preset live sur vrai cash (`service/dca/atr/bench/`)

Le preset lié par un binding est **en plus** dimensionné sur le portefeuille réel, en LECTURE SEULE (aucun ordre, jamais). La chaîne mock (wallet mock, `actionType`, `cashAfter`, performance) est inchangée ; les presets sans binding se comportent exactement comme avant.
- **Port** `RainbowPortfolioSource` : `read(preset)` → `PortfolioReading(cash USD, cashByMember, positions, fetchedAt, status OK|STALE|UNAVAILABLE|NOT_TRADABLE, walletId)` ; `liveSlots(user)` (presets liés triés par `priority`, vide côté mock) ; `checkFreshness`. Implémentations : `MockPortfolioSource` (wallet mock, via `PortfolioView`) et `RealPortfolioSource` (seul bean du bench à toucher l'exchange : `BindingCheck` à chaque passe, puis soldes disponibles via `ReadOnlyBalanceReader`, cache 60 s). Périmètre BTC/ETH/PAXG + membres du groupe `USD` (cash = USDC + USDT, détail par membre conservé), autres soldes ignorés. Panne, clé rejetée, binding KO, lecture sans aucun solde du périmètre ⇒ `UNAVAILABLE` (jamais un 0 silencieux). Couple `NOT_TRADABLE_WITHOUT_FIAT` ⇒ `NOT_TRADABLE` (soldes non lus, aucune action, `blockReason=NOT_TRADABLE_WITHOUT_FIAT`) ; le mock du preset reste utilisable. Chaque `BindingCheck` (création, mise à jour, vérification, passe) persiste `tradability`, `quoteMember`, `bridgePair`, `tradabilityCheckedAt` sur le binding ; `ExecutionGuard.requireExecutable(binding)` est le point de passage obligatoire de tout futur moteur d'exécution (refus si le statut persisté n'est pas `OK`). Seuil `STALE` : `tradeio.rainbow-live.reading-stale-after` (ISO-8601, défaut `PT30M`).
- **Ordre et cash commun** : par utilisateur, presets live d'abord par `priority` croissante (puis rang d'actif), un `CashLedger` par wallet (pool USD = USDC + USDT créé à la première lecture OK). Achat accepté ⇒ cash réservé ; achat > cash restant ⇒ **tout-ou-rien**, action `BLOCKED` + `INSUFFICIENT_CASH`. Les ventes ne sont pas créditées le jour même.
- **Position tradable** = `bagPercent`/100 × position réelle (dynamique). TREND_MIX : vente = fraction du signal × position tradable (`ReferenceSizer`) ; FIXED : quantité du moteur plafonnée à la position tradable. Achat et vente le même jour : la vente l'emporte.
- **Snapshot dans chaque bloc de passe** (colonnes `t2355_live_*` / `t0005_live_*`) : `liveStatus`, `liveWalletId`, `liveFetchedAt`, `liveCashUsd`, `livePositionQty`, `liveTradableQty`, `liveCashReserved` (déjà consommé par les actifs servis avant), `liveBlockReason` (`NONE|INSUFFICIENT_CASH|UNAVAILABLE`), `liveActionType` (`BUY|SELL|NONE|BLOCKED`), `liveActionAmountUsdc`, `liveActionQuantity`. Nuls pour un preset non live. `UNAVAILABLE`/`STALE` ⇒ `NONE` + raison `UNAVAILABLE`, WARN.
- **Rejeu 23:55** : snapshot et action live d'origine conservés (comme l'action mock) ; un achat d'origine reste réservé dans le pool. **00:05** : relit le snapshot de 23:55 du jour s'il est encore frais (pas de nouvel appel exchange incohérent), sinon nouvelle lecture ; l'action live n'est jamais appliquée.
- **Garde** `RainbowLiveNoExchangeDependencyTest` : seules les implémentations de `RainbowPortfolioSource` peuvent dépendre de `service.connector`/`Wallet`/`ProviderApiService` dans le package du bench ; le port n'a aucune méthode d'ordre.
- **Limite** : lecture seule ⇒ le solde réel ne bouge pas avec les actions recommandées ; le moteur avance comme si elles avaient eu lieu, y compris achat bloqué.
