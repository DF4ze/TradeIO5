# Rainbow DCA ATR live — Affectations, signal quotidien, liens (bindings), API REST

Vérifié le : 2026-11-07 (`service/expert/*`, `controller/Expert*`, `model/dto/expert/ExpertDtos`, `service/market/instrument/*`, `service/connector/{instrument,fee,orderbook}`, `service/dca/atr/binding/BindingPathQuoteService`, `model/entity/dca/bench/*`, `repository/dca/bench/*`, `service/dca/atr/bench/{AssetAffectationService,ExpertBasePresetService,AffectationConfigResolver,AffectationMigrationService,RainbowLiveRunService,RainbowLiveBindingRunService,RainbowLiveExecutionService,RainbowTrendLiveService,RainbowLiveQueryService,RainbowLiveDefaultPresets,RealPortfolioSource,LiveSizing,CashLedger}`, `model/dto/dca/bench/RainbowLiveDtos`, `service/scheduler/RainbowLivePass2355Job`, `configuration/initializer/{ExpertBasePresetInitializer,AffectationMigrationInitializer}`, `controller/RainbowLive{,Admin}Controller`, `controller/RainbowLiveControllerAdvice`, `templates/userPage.html`, `templates/fragments/rainbowLive.html`, `static/assets/js/rainbow-live.js`, `static/assets/css/rainbow-live.css`).

Périmètre : persistance + moteur câblé + **une passe quotidienne à 23:55 UTC** (job désactivé par défaut) + déclenchement admin + API REST utilisateur (Affectations, activation, liens, wallet réel) + écrans `/app/**`. La passe calcule le **signal** de chaque Affectation active, le dimensionne sur le **portefeuille réel en lecture seule** (par lien) et alimente le plan d'ordres ([`10-execution-plan.md`](10-execution-plan.md)). Aucun appel exchange hors lecture de marché, lecture des soldes (`RealPortfolioSource`) et exécution réelle verrouillée (test de garde `RainbowLiveNoExchangeDependencyTest`). Le moteur pur reste `service/dca/atr/RainbowAtrEngine` (cf. [`04-market-data.md`](04-market-data.md)).

Il n'existe **aucun wallet fictif ni performance simulée** : le signal d'une Affectation n'est jamais plafonné par un portefeuille, seul le dimensionnement par lien (portefeuille réel) l'est.

## Entités (schéma créé par `ddl-auto=update` ; migration Flyway préparée mais non activée, cf. [`../operations/flyway.md`](../operations/flyway.md))

- `TrendPreset` (`trend_preset`) : réglages du Trend Mix (colonnes typées `TrendMixCalculator.Params`), `rangeMapping` (`KEEP_PREVIOUS|TO_BEAR|TO_BULL` : jeu retenu quand le Trend est RANGE), `assetSymbol` (BTC|ETH|PAXG), `name`, `origin` (`PresetOrigin` SYSTEM|USER), `owner` (nul pour SYSTEM), `baseRole` (`BasePresetRole` : `TREND` pour le preset de base, nul sinon), `revision`, `createdAt`/`updatedAt`. **Unique (asset, base_role)** pour les presets de base et **(owner, asset, name)** pour ceux des utilisateurs.
- `RainbowPreset` (`rainbow_preset`) : `@Embedded RainbowAtrConfig` + `analysisWindowMonths`, mêmes colonnes d'identité (`assetSymbol`, `name`, `origin`, `owner`, `baseRole` ∈ `RAINBOW_BULL|RAINBOW_BEAR|null`, `revision`) et mêmes unicités. **Neutre** : c'est l'Affectation qui l'installe sur UP ou sur DOWN (le même preset peut occuper les deux emplacements).
- `AssetAffectation` (`asset_affectation`) : **une par (user, actif)** (unique), `trendPreset`, `rainbowUp`, `rainbowDown` (FK vers les presets de l'actif, système ou propres à l'utilisateur), `enabled` (activation par l'utilisateur : seule une Affectation active et complète est jouée par la passe, `PATCH /affectations/{id}/enabled`), `createdAt`/`updatedAt`. `isComplete()` = les trois presets présents ; `label()` = « <nom Up> / <nom Down> ». Le Trend choisit chaque jour le preset Rainbow joué : UP ⇒ `rainbowUp`, DOWN ⇒ `rainbowDown`, RANGE selon `rangeMapping`.
- `RainbowAtrConfig` (`@Embeddable`) : 1 colonne typée par paramètre = `RainbowAtrTuning` (17) + `RainbowAtrGlobals` (12 + `multX2/X1/X0_5/Triggered` + `baseAmount`). `of(tuning, globals)`, `toTuning()`, `toGlobals()`, `hash()` (SHA-256 tronqué). `baseAmount` n'existe que dans la config. Réutilisé tel quel (mêmes noms de colonnes) comme snapshot dans le run.
- **Presets système de base** (`ExpertBasePresetService`, `ExpertBasePresetInitializer` `@Order(61)`) : 9 presets, 3 par actif — « Trend de base » (`TREND`), « <actif> Bull » (`RAINBOW_BULL`, jeu de `RainbowLiveDefaultPresets`/`RainbowAtrPresets`) et « <actif> Bear » (`RAINBOW_BEAR`). Créés s'ils sont absents, **jamais modifiés** ; une relance ne duplique rien. `AssetAffectationService#ensureAffectations(user)` (appelé par la passe et par `GET /affectations`) crée, pour chaque actif où l'utilisateur n'en a pas, une Affectation **inactive** sur ces presets de base (Bull ⇒ UP, Bear ⇒ DOWN).
- `RainbowLivePresetEvent` (`rainbow_live_preset_event`) : historique des changements d'Affectation d'un user (`type` ENABLE | DISABLE | LIVE_SWITCH, `assetSymbol`, libellé avant/après sans FK, `occurredAt` via `DomainClock`, `reason`), `ON DELETE CASCADE` sur le user. Écrit par `RainbowLivePresetEventService` : activation/désactivation effective, changement des presets installés, création/bascule d'un binding (`LIVE_SWITCH`).
- `RainbowLiveEngineState` (`rainbow_live_engine_state`) : unique (Affectation, `state_day`), `ON DELETE CASCADE` ; état de la machine Rainbow (`RainbowAtrState` : armements, verrou, cooldown, réserve moon, automate moon) + **`positionQty`** (position VIRTUELLE du moteur, base de la réserve moon et des ventes, indépendante de tout wallet) + `configHash` (empreinte de la config effective : fenêtre + presets Rainbow UP/DOWN + preset Trend) à la FIN du jour. NaN stockés `null`.
- `RainbowAthReference` (`rainbow_ath_reference`) : unique (actif, `ref_day`) ; ATH par ACTIF valable à la fin du jour (une ligne par jour : le run du lendemain relit l'ATH de la veille).
- `RainbowLiveBinding` (`rainbow_live_binding`) : lien (user, actif, wallet) → **wallet réel** (lecture seule) ; l'Affectation jouée est celle de (user, actif) (`affectation` FK, posée à la création). **Unique (`user_id`, `asset_symbol`, `wallet_id`)** (`uk_rainbow_live_binding_user_asset_wallet`) ⇒ un binding par actif **et par wallet**. Une Affectation peut alimenter plusieurs bindings (`findAllByAffectation`). Champs : `wallet` (FK `Wallet`, doit appartenir au user), `bagPercent` (0-100, défaut 100, part **dynamique** de la position réelle offerte à la stratégie), `simulation` (boolean, défaut faux) et `minBuyUsd` (nullable : achat minimum du lien, sous lequel l'achat est reporté en carry), `priority` (ordre de passage du cash, défaut = rang dans `RainbowLiveDefaultPresets.ASSETS` : BTC 0, ETH 1, PAXG 2). **Mode d'exécution** dérivé (`BindingExecutionMode`) : `executionEnabled` ⇒ `ACTIVE`, sinon `simulation` ⇒ `SIMULATION`, sinon `DISABLED` ; `applyExecutionMode` garde les deux booléens exclusifs. Donnée utilisateur créée par l'API, jamais par un initializer. Lu par le moteur via `RealPortfolioSource.read(binding)`. **Retrait = archivage** : `DELETE /api/rainbow-live/bindings/{id}` pose `archived_at` (colonne nullable, créée par `ddl-auto=update`), coupe l'exécution et remet à zéro l'armement / la confirmation du 1ᵉʳ ordre ; la ligne et ses `RainbowLiveBindingRun` restent (historique), mais un lien archivé est ignoré partout (`findByUser…` et la liste admin l'excluent, `owned()` et `arm` répondent 404, onboarding et candidats le traitent comme absent). Relier le même (actif, wallet) **réactive** la ligne archivée (même id, paramètres réinitialisés, exécution coupée, 1ᵉʳ ordre à re-valider). Pas de purge automatique pour l'instant.
- `RainbowLiveRun` (`rainbow_live_run`) : **unique (Affectation, `run_day`)**, `ON DELETE CASCADE` sur l'Affectation ; `user`, `assetSymbol`, `day` (jour UTC), un bloc `@Embedded RainbowLivePassBlock signal` (colonnes `signal_*`), `config` (snapshot) + `configHash`. Signal **par Affectation**, non plafonné.
- `RainbowLivePassBlock` : `close`, `sma`, `atr`, `boundDown2`/`boundDown1`/`boundUp1`/`boundUp2`/`boundUp3` (SMA ± ATR×mult correspondant), `zone`, `athDistance`, `buyFactor`/`sellFactor`, `moonMode`, `buyArmed`/`sellArmed`/`buyLocked`, `cooldownRemaining`, `moonReserveQty`, `activeSet` (nom du preset Rainbow joué) et `trendRegime` (UP/DOWN/RANGE), action décidée (`RainbowLiveAction` BUY/SELL/NONE, `actionAmountUsdc`, `actionQuantity`, `actionPrice`), `configHash`, `computedAt`.
- `RainbowLiveBindingRun` (`rainbow_live_binding_run`) : **unique (binding, `run_day`)**, `ON DELETE CASCADE` sur le binding ; snapshot live **par lien** : un bloc `@Embedded RainbowLiveLiveBlock live` (colonnes `live_*`), `computedAt`.
- `RainbowLiveLiveBlock` : `status` (`PortfolioStatus` OK|UNAVAILABLE|NOT_TRADABLE), `walletId`, `fetchedAt`, `cashUsd`, `cashDetail` (JSON par membre du groupe USD), `positionQty`, `tradableQty`, `cashReserved` (déjà consommé par les actifs servis avant), `blockReason` (`NONE|INSUFFICIENT_CASH|NOT_TRADABLE_WITHOUT_FIAT|UNAVAILABLE`), `actionType` (`BUY|SELL|NONE|BLOCKED`), `actionAmountUsdc`, `actionQuantity`, `candleSource` (exchange réel des candles du signal du lien), `candleSourceSubstituted`.

Suppression d'une Affectation ⇒ runs et états supprimés par FK. Les presets sont référencés, jamais copiés : modifier un preset installé change la config effective de l'Affectation (voir `AffectationConfigResolver`), sans écrire ni recalculer de run.

## Sémantique du run (`RainbowLiveRunService`)

Horloge `DomainClock` (`computedAt`) ; un run par (Affectation, jour UTC).
- **`upsert(affectation, day, block)`** (passe du jour, 23:55 UTC) : crée le run ou, sur rejeu du même jour, remplace les indicateurs en **conservant l'action d'origine**. `discardDay(user, day)` supprime les runs d'Affectation d'un utilisateur pour un jour (recalcul forcé, cf. ci-dessous).
- **`refresh(affectation, day, closedBlock)`** (passe du lendemain) : remplace les indicateurs d'un run existant par ceux calculés sur la bougie désormais **clôturée** ; l'action décidée à 23:55 reste figée. Sans run ce jour-là : `false`, rien n'est écrit (pas de rattrapage). `hasSignal(affectation, day)` conditionne le rafraîchissement.
- Chaque écriture rafraîchit le snapshot de config du run et le hash (aussi stocké dans le bloc) ; comparer au hash effectif de l'Affectation détecte « config modifiée ».
- `RainbowLiveBindingRunService` : `snapshotOf(binding, day)` / `upsert(binding, day, block)` ; rejeu du même jour : snapshot live existant conservé ; `discardDay(user, day)` supprime les snapshots de lien d'un utilisateur pour un jour (recalcul forcé).

## Affectations (`AssetAffectationService`)

`ensureAffectations(user)`, `forAsset(user, actif)`, `list(user)`, `get(user, id)`, `setEnabled(user, id, enabled)` (événement ENABLE/DISABLE si l'état change), `assign(user, actif, trendId, upId, downId)` : installe trois presets de l'actif (système ou propres à l'utilisateur ; ceux d'un autre utilisateur ou d'un autre actif sont refusés), **purge les états moteur** de l'Affectation (`deleteByAffectation`) et écrit un événement `LIVE_SWITCH`. Opérations réservées au propriétaire ; erreurs typées : `AssetAffectationNotFoundException` (inexistante **ou** d'un autre user) ⇒ 404.

**Config effective** (`AffectationConfigResolver`) : accesseur unique de la config d'une Affectation (`config` = preset DOWN, `analysisWindowMonths`, `trendConfig`, `effectiveHash`), lue à chaque appel dans les presets installés. Modifier un preset ou changer les presets installés s'applique à la passe suivante : le hash effectif change et `RainbowTrendLiveService` ré-amorce l'état moteur (cf. plus bas), de sorte que le moteur bascule immédiatement sur les résultats de la nouvelle config.

**Migration au démarrage** (`AffectationMigrationInitializer` `@Order(62)` → `AffectationMigrationService#migrate`, idempotente) : à partir des anciens presets utilisateur (tables legacy en lecture seule, cf. [`../known-gaps/nettoyages.md`](../known-gaps/nettoyages.md)), crée l'Affectation de chaque (user, actif) qui n'en a pas. Preset retenu = celui référencé par un binding, sinon l'actif, sinon le plus ancien. Ancien preset sans réglages Trend propres ou identique aux défauts ⇒ presets système de base ; sinon Trend et/ou Rainbow UP/DOWN propres à l'utilisateur (créés seulement s'ils diffèrent de la base). Runs, états moteur et bindings du preset retenu sont rattachés à l'Affectation avec le même `configHash` (aucun ré-amorçage) ; runs et états des autres presets sont supprimés (journalisés), leurs bindings rattachés. Les colonnes `preset_id` des tables concernées deviennent nullables. Sans ligne legacy, ne fait rien ; une relance ne crée aucun doublon.

## Passe quotidienne (`RainbowLiveExecutionService#runPass(asOf[, dayOverride])`)

Une seule passe par jour, à **23:55 UTC**, sur la bougie D1 **du jour encore ouverte** (valeurs provisoires), comptabilisée sur le **jour UTC courant** (`dayFor(asOf)` = date UTC de `asOf`) : le signal tombe sur la bougie du jour affichée par l'exchange. Horloge injectée (`DomainClock` dans le job/l'endpoint, `asOf` explicite en test) ; `synchronized` (cron et déclenchement manuel ne se chevauchent pas). `dayOverride` (endpoint) force le jour.

- **Utilisateurs/Affectations** : pour chaque `User` `enabled` non archivé, `ensureAffectations` puis Affectations `enabled` et complètes. Clé user jamais codée en dur. Une erreur (user, actif) est comptée et n'arrête jamais les autres ; pas de rattrapage des jours manqués.
- **Données** : `MarketDatasetEngine.getDailyDatasetForAsset(actif, D1_LOOKBACK_CANDLES, asOf, source)` — chemin D1 **natif** (hors Bucket H1, cf. [`04-market-data.md`](04-market-data.md#chemin-d1-natif-rainbow-getdailydatasetforasset)), chargé **une fois par (actif, source, passe)** et partagé entre Affectations/users. `source` = exchange du wallet du lien (`LiveCandleSource`, `null` si wallet sans exchange de marché : défauts `asset_provider`). La bougie du `day` est repérée par sa date UTC ; la bougie du jour suivant, éventuelle, est ignorée ; bougie absente ⇒ WARN, série sautée (pas d'exception). Dataset plus court que le warmup du preset Trend de l'Affectation ⇒ Affectation sautée.
- **Rafraîchissement J-1** (`refreshPreviousDay`, avant le run du jour) : si l'Affectation a un run la veille, elle est rejouée sur la série tronquée à J-1 (bougie désormais clôturée) : indicateurs, état moteur + position virtuelle + ATH (`Outcome#commit` seulement si le run existait). **L'action décidée la veille reste figée.** Une erreur ici est un WARN et n'empêche pas le run du jour.
- **Signal par lien** : l'Affectation est calculée sur la source de son lien le plus prioritaire qui a un exchange (défauts sans lien). Sa machine d'état est unique : elle partage son signal entre ses liens, avec WARN si les sources diffèrent (lien marqué substitué). Source indisponible ⇒ fallback `asset_provider` avec WARN bruyant ; le snapshot du lien porte `candleSource` et `candleSourceSubstituted`.
- **Fenêtre** : `RainbowLiveDefaultPresets.D1_LOOKBACK_CANDLES` = **720** (limite native Kraken `OHLC` D1, test de garde). L'ATH de référence est persisté par actif (`RainbowAthReference`). Voir [`../known-gaps/rainbow-dca-chantiers-ouverts.md`](../known-gaps/rainbow-dca-chantiers-ouverts.md).
- **Action du jour** : un pas de `RainbowAtrStrategy#step` : achat ⇒ BUY (montant moteur en USDC), vente ⇒ SELL. Achat et vente sur la même bougie : la **vente l'emporte** (WARN). Le signal n'est **plafonné par aucun portefeuille** ; il est transmis en `LiveDemand` (achat voulu, vente = fraction × position) puis dimensionné par lien.
- **Persistance** : bloc `RainbowLivePassBlock` complet via `RainbowLiveRunService#upsert`. Retour : `PassSummary(day, processed, skipped, errors)`.

## Dimensionnement sur le portefeuille réel (par lien)

Une Affectation liée par au moins un binding est dimensionnée, **une fois par lien**, sur le portefeuille réel en LECTURE SEULE (aucun ordre). Une Affectation sans lien produit son signal (run) mais aucun run de lien.
- **Port** `RainbowPortfolioSource` : `liveSlots(user)` (`LiveSlot(bindingId, affectationId, assetSymbol, walletId, priority, bagPercent, candleSource)` triés par `priority`). Implémentation `RealPortfolioSource` (seul bean du bench à toucher l'exchange) : `read(binding)` → `PortfolioReading(cash USD, cashByMember, positions, fetchedAt, status OK|UNAVAILABLE|NOT_TRADABLE, walletId)` ; `BindingCheck` à chaque passe, puis soldes disponibles via `ReadOnlyBalanceReader`, cache 60 s. Périmètre BTC/ETH/PAXG + membres du groupe `USD` (cash = USDC, détail par membre conservé ; le stock en transit actif est déduit de la position du lien portant la même devise), autres soldes ignorés. Panne, clé rejetée, binding KO, lecture sans aucun solde du périmètre ⇒ `UNAVAILABLE` (jamais un 0 silencieux). `NOT_TRADABLE_WITHOUT_FIAT` ⇒ `NOT_TRADABLE` (soldes non lus, aucune action). Chaque `BindingCheck` persiste `tradability`, `quoteMember`, `routeKey`, `tradabilityCheckedAt` sur le binding ; `ExecutionGuard.requireExecutable(binding)` est le point de passage obligatoire de l'exécution (refus si le statut persisté n'est pas `OK`).
- **Ordre et cash commun** (`CashLedger`) : par utilisateur, liens d'abord par `priority` croissante (puis rang d'actif, puis `bindingId`), un ledger par wallet (pool USD = USDC créé à la première lecture OK). Achat accepté ⇒ cash réservé ; achat > cash restant ⇒ **tout-ou-rien**, action `BLOCKED` + `INSUFFICIENT_CASH`. Les ventes ne sont pas créditées le jour même.
- **Position tradable** = `bagPercent`/100 × position réelle (dynamique) ; vente plafonnée à la position tradable (`LiveSizing`). Achat et vente le même jour : la vente l'emporte.
- **Snapshot par lien** (`RainbowLiveBindingRun`) : voir `RainbowLiveLiveBlock`. Une panne d'un lien n'affecte pas les autres. `UNAVAILABLE` ⇒ `NONE` + raison `UNAVAILABLE`, WARN.
- **Recalcul forcé du jour** : `RainbowLiveExecutionService#recomputeDay(user, asOf, day)` supprime les runs d'Affectation et de lien de l'utilisateur pour le jour puis rejoue sa passe sur la bougie courante (action figée et réservation de cash levées ; le `CashLedger` n'est pas persisté). Déclenché par le reset d'un plan du jour UTC ouvert ([`10-execution-plan.md`](10-execution-plan.md)), jamais si un ordre est parti.
- **Rejeu du même jour** : snapshot et action live d'origine conservés ; un achat d'origine reste réservé dans le pool (pas de nouvelle lecture exchange). Le lendemain, une nouvelle lecture est faite pour le nouveau jour ; le snapshot de la veille n'est pas modifié.
- **Garde** `RainbowLiveNoExchangeDependencyTest` : seules les implémentations de `RainbowPortfolioSource` peuvent dépendre de `service.connector`/`Wallet`/`ProviderApiService` dans le package du bench ; le port n'a aucune méthode d'ordre.

## Moteur Trend → Rainbow (`RainbowTrendLiveService`)

Pour chaque Affectation, `RainbowLiveExecutionService` délègue à `RainbowTrendLiveService#run(day, affectation, candles, dataset, dayIdx)` :

1. **Trend** : `TrendMixCalculator` (réglages du `TrendPreset`, cf. [`09-trend.md`](09-trend.md)) sur la série D1 chargée, puis `RainbowSetSelector` (RANGE selon `rangeMapping`, DOWN au départ) → preset Rainbow joué : UP ⇒ `rainbowUp`, DOWN ⇒ `rainbowDown`. Le montant de base est celui du preset joué. Les runs écrits restent figés (snapshot de config + `configHash` par run).
2. **État et position virtuelle** : dernière ligne `RainbowLiveEngineState` antérieure au jour **si son `configHash` == `AffectationConfigResolver#effectiveHash`**. Absente (1re passe), hash différent (preset modifié ou presets installés changés) **ou trou de passes** (dernier `state_day` antérieur à la bougie précédant le jour : service arrêté, série sautée faute de bougie) ⇒ (ré-)amorçage par `RainbowAtrReplay.runFull` sur `analysisWindowMonths` mois jusqu'à la veille avec la config courante (état + `finalPosition()`), enregistré pour la veille. Un trou est tracé (WARN + journal admin `AdminAction.RUN`, acteur `auto-resync`, cible `rainbow-resync:affectation:<id>`, payload `reason`/`lastStateDay`/`resyncedTo`) : sans ce rejeu, un événement manqué (ex. levée du verrou d'achat par une clôture < DOWN2) ne serait jamais vu. Les jours manqués ne produisent **ni run ni ordre** : seul l'état moteur avance. Sans changement ni trou, l'état est recalculé depuis celui de la veille (un seul `RainbowAtrStrategy#step`).
3. **ATH** : `RainbowAthService#athBefore` (ATH de la veille, lu en base). Amorçage one-shot à la 1re demande d'un actif sans aucune ligne : historique D1 complet Binance (`BinanceDailyCandleFetcher`, klines publics, seul appel exchange hors portefeuille, une fois par actif).
4. **Dimensionnement du signal** : `ReferenceSizer` (base × facteur ATH × multiplicateur de zone ; vente = fraction × position **virtuelle**), sans plafond de portefeuille.
5. **Écritures** : état du jour, position virtuelle (`max(0, position − quantité vendue + montant acheté / close)`) et ATH du jour via `Outcome#commit`, après l'enregistrement du run. Le run du lendemain rejoue le jour sur la vraie clôture (même chemin) et **remplace** ces écritures. Rejouer une passe est idempotent.

Validation des réglages Trend : `RainbowLiveTrendConfigs#validate` (fenêtres ≥ 2, `0 ≤ exit ≤ enter`, `confirm ≥ 1`, tunings valides, `baseAmount > 0`).

## Job et déclenchement manuel

`RainbowLivePass2355Job` : propriété `tradeio.rainbow-live.pass-2355-cron`, défaut `-` (désactivé), `zone = "UTC"` explicite, cron cible `0 55 23 * * *` (cf. [`operations/scheduled-jobs.md`](../operations/scheduled-jobs.md)). Manuel : `POST /api/admin/rainbow-live/run[?day=YYYY-MM-DD]` (ADMIN, `RainbowLiveAdminController`, réponse = `PassSummary`). Pas de déclenchement manuel côté user.

**Resynchronisation de l'état moteur** (`RainbowLiveExecutionService#resync` → `RainbowTrendLiveService#resync`) : ramène l'état des Affectations actives (ou d'une seule) à la veille (dernière bougie clôturée, série bornée à la veille) par `RainbowAtrReplay.runFull`, sans run ni ordre ; toute la chaîne d'états de l'Affectation est d'abord supprimée (la passe rejoue la veille à partir de l'état d'avant : il doit être sain ou absent, auquel cas la passe ré-amorce) ; sans `force`, un état déjà à jour (même config effective, dernier `state_day` ≥ veille) n'est pas recalculé. Réponse `ResyncSummary(toDay, resynced, upToDate, skipped, errors)` ; série indisponible (bougie de la veille absente) ⇒ « sautée », rattrapée par la détection de trou de la passe suivante. Déclencheurs : (1) **au démarrage** (`service/scheduler/RainbowLiveResyncRunner`, `ApplicationReadyEvent`, propriété `tradeio.rainbow-live.resync-on-startup=true`, absente en test ; une erreur n'empêche jamais le démarrage) ; (2) **admin** `POST /api/admin/rainbow-live/resync[?affectationId=]` (forcée, tracée au journal admin avec le nom de l'admin) ; (3) automatiquement par la détection de trou de chaque passe (ci-dessus). Traçabilité : toujours `AdminAction.RUN` (pas de valeur d'enum dédiée : la colonne MySQL est un `enum` non migré par `ddl-auto`).

**Instantané de patrimoine** (`PortfolioSnapshotService`, `portfolio_snapshot` + `portfolio_snapshot_asset`) : en fin de passe, une ligne **immuable** par (user, wallet, jour UTC) : statut de la lecture, stable (`cashUsd`), valeur des actifs, patrimoine, exposition %, bande d'exposition de l'utilisateur en vigueur (`exposureMin/Max`), base de prix `D1_OPEN_2355` (clôture de la bougie D1 encore ouverte, la même que le signal) ; une ligne d'actif (quantité, prix, valeur) par actif détenu ou lié. Réutilise la **lecture de la passe** (aucun appel exchange en plus) : pas de lecture ⇒ pas d'instantané. Lecture non `OK` ⇒ statut conservé, valeurs nulles (jamais 0) ; prix manquant pour un actif détenu ⇒ totaux et exposition nuls. Idempotent (unicité user/wallet/jour : un rejeu ne réécrit rien), pas de rattrapage ni de reconstruction rétroactive ; le provider se déduit de `wallet.exchange`. Lecture : `PortfolioSnapshotRepository` (aucun endpoint encore, cf. [`../graphique/inventaire-options-affichage.md`](../graphique/inventaire-options-affichage.md) §6).

## Bindings et vérification de disponibilité (`service/dca/atr/binding/`)

- `RainbowLiveBindingService` : CRUD scopé au user (binding ou wallet d'un autre user ⇒ `RainbowLiveBindingNotFoundException` ⇒ 404 ; binding déjà existant pour (actif, wallet) ⇒ 409 ; `bagPercent` hors [0,100], actif inconnu ⇒ 400). Création et modification retournent le résultat de `BindingCheck` sans le persister : un KO n'empêche pas l'enregistrement.
- `BindingCheck` (appelable depuis le moteur) → `BindingCheckResult(status, message, quoteMember, routeKey)` (`isOk()` = OK ou TRADABLE_VIA_INTERMEDIARY : lecture autorisée ; `isExecutable()` = OK seul, tant que l'exécution multi-jambes n'existe pas ; `isBlocked()` = NOT_TRADABLE_WITHOUT_FIAT), jamais d'exception métier. Ordre : wallet activé (`WALLET_DISABLED`) → credential active (`CREDENTIAL_INVALID`) → lecteur + vérificateur pour l'exchange (`PROVIDER_UNSUPPORTED`) → lecture des soldes via `ReadOnlyBalanceReader` (`CredentialRejectedException` = clé/signature/passphrase/permission/IP rejetées ⇒ `CREDENTIAL_INVALID` ; autre panne ⇒ `BALANCE_UNAVAILABLE`) → chemin spot **sans monnaie fiat** (USDC, catalogue en base) : paire `<actif>/USDC` ⇒ `OK` ; sinon route via un intermédiaire choisi (BTC, `PathFinder`) ⇒ `TRADABLE_VIA_INTERMEDIARY` (`quoteMember`, `routeKey` ex. `USDC>BTC>PAXG`, mémorisée sur le lien) ; sinon `NOT_TRADABLE_WITHOUT_FIAT` ; catalogue absent et exchange injoignable ⇒ `INSTRUMENT_UNAVAILABLE`. Solde nul accepté, clé absente de la map = solde 0 (pas indisponible) ; les soldes ne sont ni conservés ni exposés.
- **Catalogue d'instruments** (`service/market/instrument/InstrumentCatalog`, table `exchange_instrument` : provider, `inst_id` `BASE-QUOTE` normalisé, base, quote, `state`, `min_sz`, `lot_sz`, `tick_sz`, `cost_min` (nullable ; Kraken `costmin`), `native_pair` (nullable ; Kraken `altname`), `fee_currency` (nullable ; Kraken `fee_volume_currency`), `fetched_at`, unique (provider, inst_id)) : lu par `BindingCheck` et `PathFinder`. Alimenté par **un seul** appel public « toutes les paires » par exchange via `InstrumentListClient` (`OkxInstrumentListClient` : `GET /api/v5/public/instruments?instType=SPOT`, `state=live` ; `KrakenInstrumentListClient` : `GET /0/public/AssetPairs`, noms normalisés par `KrakenAssetNames`, `status=online`, paires `.d` ignorées). Rafraîchi à la demande quand il a plus de 24 h (`tradeio.execution.instrument-catalog.refresh-after`, défaut `PT24H`) ou via `refresh(provider)` ; panne ⇒ catalogue conservé (WARN), jamais vidé, pas de nouvelle tentative avant 5 min ; catalogue absent et exchange injoignable ⇒ `InstrumentLookupException` ⇒ `INSTRUMENT_UNAVAILABLE`. Pas de checker Binance (pas de wallet Binance).
- `WalletInitializer` ne crée plus de wallet Binance ; il crée le wallet « OKX » (credential OKX si présente) en plus de Kraken/Binance Test/Ledger. Les lignes déjà en base ne sont pas touchées.

## Chemin d'achat chiffré : frais, carnet, PathFinder, Fee Test (lecture seule, aucun ordre)

Calcul **à la demande** (`GET /api/rainbow-live/bindings/{id}/path-quote?amount=`, cf. [`../api/rest-endpoints.md`](../api/rest-endpoints.md)) ; aucun job, aucune écriture hors cache du catalogue. `BindingPathQuoteService` (`service/dca/atr/binding`) : binding du user (sinon 404) → soldes du wallet (`ReadOnlyBalanceReader`) filtrés sur les membres du groupe `USD` (sources) → catalogue → `PathFinder` avec un marché réel (`LegMarketSource`).
- **Frais réels** : `TradingFeeProvider` / `OkxTradingFeeProvider` (`GET /api/v5/account/trade-fee?instType=SPOT&instId=…`, clé Read du wallet, signature HMAC partagée avec `OkxBalanceReader` dans `OkxSignedRequests`). Taux OKX signés (négatif = frais payé) normalisés en `FeeRate(makerPct, takerPct)` en % (positif = coût) ; champs `maker/taker` pour les paires USDT, `makerUSDC/takerUSDC` pour les paires USDC ; champ absent ⇒ `BalanceUnavailableException` (jamais de frais supposé). Cache mémoire 24 h sur `DomainClock` (échecs non cachés), throttle 500 ms entre appels réseau. Compte OKX de Clem (EEA, niveau « Utilisateur régulier ») : 0,10 % maker / 0,20 % taker, 0 % sur `USDC-USDT`. Le coût d'une jambe utilise le taux **taker** (ordres limit IOC prévus). Clé rejetée (50100-50114) ⇒ `CredentialRejectedException`.
- **Frais réels Kraken** : `KrakenTradingFeeProvider` (`POST /0/private/TradeVolume` `pair=<nativePair>&fee-info=true`, clé Read, signature `KrakenSignedRequests`). `fees` = taker, `fees_maker` = maker, déjà en % ; champ absent ⇒ `BalanceUnavailableException`. Cache 24 h par (clé, instrument), échecs non cachés, throttle 1 s.
- **Carnet public** : `OrderBookClient` / `OkxOrderBookClient` (`GET /api/v5/market/books?instId=&sz=50` → `OrderBookSnapshot`) ; repli `GET /api/v5/market/ticker` (un niveau par côté) marqué `estimation=TICKER` (slippage non chiffré). Un appel par devis, pas de cache. Kraken : `KrakenOrderBookClient` (`GET /0/public/Depth?pair=<nativePair>&count=`, repli `/0/public/Ticker` marqué `TICKER`), paire lue au catalogue (`nativePair`, repli `KrakenAssetNames.fallbackPair`) ; le catalogue expose des `inst_id` en symboles standard (`KrakenAssetNames`).
- **`PathFinder`** (`service/market/instrument`, pur) : arêtes BUY `QUOTE→BASE` (ask) et SELL `BASE→QUOTE` (bid) pour chaque paire du catalogue ; paires touchant un nœud interdit ignorées (fiat : `ExecutionDefaults.FIAT_CURRENCIES` ; `USDT` ; surcharge `tradeio.execution.forbidden-nodes`, liste CSV) ; sources = devises détenues ; profondeur ≤ `MAX_PATH_DEPTH` (2), énumération exhaustive. Intermédiaires autorisés `ExecutionDefaults.INTERMEDIARIES` (BTC, ETH), choisis automatiquement `CHOSEN_INTERMEDIARIES` (BTC seul) : une route ETH est chiffrée et exposée (`chosen=false`), jamais retenue. Coût d'une jambe = frais taker + demi-spread + slippage au montant (VWAP du carnet, `BookSlippage`) ; route = **somme brute**. Jambes dimensionnées en séquence sur le **net reçu** de la précédente ; `sz` ⌊⌋ au `lotSz` en BUY, ⌈⌉ en SELL, `minSz`/`costMin` ⇒ `BELOW_MIN`. Résultat `PathQuote(status OK|NO_PATH|BELOW_MIN, source, legs[], totalCostPct, feeTestLevel, estimation BOOK|TICKER, underfunded, routeKey, routes[RouteQuote])` ; `NO_PATH` ⇒ « non tradable sans monnaie fiat ». Vente : route vers USDC (`X>USDC` ou `X>BTC>USDC`).
- **`FeeTest`** (pur) : coût total < `warn-pct` ⇒ GREEN ; de `warn` à `red` **inclus** ⇒ WARNING ; > `red` ⇒ RED. Seuils lus à chaque appel dans `ExecutionControl.feeWarnPct` / `feeRedPct` via `ExecutionControlService` (défauts 0,2 / 0,8 posés par `ExecutionControlInitializer`, qui lit d'abord les propriétés `tradeio.execution.fee-test.warn-pct` / `red-pct` si la base est vide ; éditables dans l'onglet admin « Plafonds »). `new FeeTest()` / `new FeeTest(warn, red)` = seuils fixes (tests). Pourcentages exposés en %, jamais en bps.
- Gardes : `ConnectorNoOrderMethodTest` et `RainbowLiveNoExchangeDependencyTest` ; aucune méthode d'ordre dans ces chemins.

## Modulation : paramètres admin et réglages utilisateur

**Principe : le Rainbow reste seul à acheter et vendre ; la modulation ne fait que changer les quantités qu'il demande** (aucun ordre de rééquilibrage). Signal (`LiveDemand`) et plan d'ordres inchangés : seul `LiveSizing` module, par lien. Roadmap : [`../prompts/prompt-roadmap-modulation-bande-puissance.md`](../prompts/prompt-roadmap-modulation-bande-puissance.md).

- **Constantes** : `service/modulation/ModulationDefaults` (défaut + bornes absolues incluses de chaque paramètre admin, valeurs neutres utilisateur 0 / 100 / 1 / 0) ; la base ne relève jamais une borne absolue.
- **Paramètres admin globaux** : singleton `RainbowModulationControl` (`rainbow_modulation_control`, id 1, `updatedAt`, `updatedBy`) : `regulationMarginPct` (25, 5–50), `sellBoostMax` (2, 1–4), `biasMax` (0,5, 0–1), `powerMin`/`powerMax` (0,25/2, 0–3), `minBandWidthPts` (10, 5–50), `modulationProductMax` (2,5, 1–5), `autonomyDays` (90, 7–365). `RainbowModulationControlService.current()` relit la base à chaque appel (sans cache), ligne absente ⇒ défauts ; `update(Params, by)` valide chaque borne et impose `powerMin ≤ 1 ≤ powerMax` (`IllegalArgumentException`, rien écrit). `RainbowModulationControlInitializer` (`@Order(71)`) crée la ligne si absente, ne modifie jamais une ligne existante.
- **Journal** : `AdminModulationService` écrit une ligne `AdminAction.MODULATION` (`target = rainbow-modulation`, payload `{before, after}`; `REFUSED` si invalide).
- **Réglages utilisateur** : `UserTradingSettings.exposureMin|exposureMax|power|bias` (`Double` **nullables** : null ⇒ neutre 0 / 100 / 1 / 0). `UserTradingSettingsService` : `getModulationSettings` (stocké ou neutre), `setModulationSettings` (validé contre `current()` : `0 ≤ min < max ≤ 100`, largeur ≥ `minBandWidthPts`, puissance dans `[powerMin, powerMax]`, `|biais| ≤ biasMax` ; ne touche jamais `riskCursor`, qui vaut `DEFAULT_RISK_CURSOR` à la création de ligne), `effectiveSettings` (valeurs stockées **clampées** aux bornes admin courantes ; bande trop étroite élargie autour de son centre, décalée pour rester dans [0, 100] ; consommé à l'étape 2).
- **API** : voir [`../api/rest-endpoints.md`](../api/rest-endpoints.md) (`/api/admin/rainbow-modulation`, `/api/user/modulation-settings`).

### Moteur de modulation (`LiveSizing`, par lien)
- **Marge de régulation réglable par l'utilisateur** : `UserTradingSettings.regulationMarginPct` (% de la largeur de bande, [5, 50], nul = défaut admin `regulationMarginPct` ; `effectiveSettings` la clampe) ; réglée dans Réglages → Modulation ; `LiveModulation` l'utilise à la place du défaut admin.
- **Calcul pur** `service/modulation/ExposureModulator` : marges de régulation `m % × (max − min)` à l'intérieur de chaque borne, `s` linéaire clampé puis `l = s²(3 − 2s)` ; achat × `(1 − l_haute)(1 + (G − 1)·l_basse)`, vente × `(1 + (G − 1)·l_haute)(1 − l_basse)` (`G = sellBoostMax`). Marge haute seulement si `max < 100`, basse seulement si `min > 0` : la bande neutre [0, 100] ne module rien. Plafond dur en USD : achat ≤ `max·V − P`, vente ≤ `P − min·V` (plancher 0).
- **Chaîne** (`LiveModulation`) : quantité du signal × `puissance·(1 ± biais)` × facteur de bande ; le produit par côté est plafonné à `modulationProductMax` ; puis plafond dur, puis les plafonds existants (cash du `CashLedger`, position tradable). Montant final = ce que lit le plan d'ordres. `effetRisque` (macro) = 1, pas encore branché.
- **Exposition** (`ExposureLedger`/`ExposureBook`, un par wallet et par passe) : `P` = Σ quantité × clôture D1 de la passe (demandes des Affectations, aucun appel exchange en plus), `V = P + cash USDC` constant ; achat accepté ⇒ `P +=`, vente ⇒ `P −=` pour le lien suivant ; rejeu du même jour : l'action d'origine met le ledger à jour. Prix manquant pour un actif détenu ou `V = 0` ⇒ exposition **inconnue** : pas de modulation de bande (puissance et biais restent appliqués), `exposureStatus = UNKNOWN` au journal.
- **`BAND_LIMIT`** (`LiveBlockReason`) : le signal voulait une action mais la modulation l'a ramenée à 0 ⇒ `NONE` + `BAND_LIMIT`.
- **Journal** : `RainbowLiveLiveBlock.modulation` (JSON, colonne `live_modulation`) : montants du signal, puissance, biais, facteurs de côté, bande, exposition avant/après, `l` haute/basse, facteurs de bande et produit, plafonds atteints, paramètres admin utilisés, montant final. Exposé en `modulation` dans le snapshot de `GET /api/rainbow-live/live-wallet`. Hors de `OrderPlanner.inputsHash` (qui ne lit que statut, action, montant, quantité, carry, cash) : le rejeu du même jour reste `unchanged`.
- Réglages neutres (aucune ligne ou colonnes nulles) ⇒ montants identiques à ceux d'avant la modulation (test de non-régression).

### Montant de base du lien

`RainbowLiveBinding.baseAmount` (`Double` nullable, choisi par l'utilisateur ; nul ⇒ montant du preset Rainbow joué). `LiveDemand` porte le montant de base avec lequel le signal a été dimensionné ; `withLinkBaseAmount` met l'**achat** à l'échelle `baseAmount lien / baseAmount du preset` (la vente, fraction de la position, n'en dépend pas) avant `LiveSizing`. Validation : > 0 et fini (`RainbowLiveBindingService`, `resetBaseAmount` remet à nul). Tests : `LiveDemandTest`, `RainbowLiveBindingControllerTest#linkBaseAmount`.

### Onboarding (`RainbowLiveOnboardingService`, `/api/rainbow-live/onboarding`)

- **Liaison** (`POST /link`) : par actif de `RainbowLiveDefaultPresets.ASSETS`, lien existant ⇒ inchangé ; sinon `BindingCheck` ; `OK` / `TRADABLE_VIA_INTERMEDIARY` ⇒ lien **inactif** sur l'Affectation de l'actif (`bagPercent`/`priority` par défaut) ; tout autre statut (non tradable sans fiat, clé rejetée, soldes illisibles…) ⇒ non lié, statut et raison retournés (rejouable).
- **Devis par exchange** (`GET /path-quotes?asset=&amount=`) : `BindingPathQuoteService#quoteWallet` sur chaque wallet actif du user, sans binding (page `/app/onboarding`, étape « Chemin d'achat » : l'utilisateur choisit l'exchange d'après le Fee Test). Un wallet en échec est retourné avec `error`, sans bloquer les autres. L'utilisateur choisit un seul couple (exchange, route) ; si la route n'est pas la moins chère, elle est mémorisée sur le lien (`RainbowLiveBinding.preferredRoute`, colonne `preferred_route`) et imposée au devis, au plan d'ordres et à l'exécution.
- **Proposition** (`GET /proposals?days=`) : `baseAmount = cash du wallet / nb de liens du wallet / (jours × multiplicateur moyen)` ; `jours` = durée choisie par l'utilisateur (champ « Étaler le cash sur », jours ou mois de 30 j), sinon `autonomyDays` admin, borné par les limites absolues de ce paramètre ; multiplicateur moyen = moyenne de `multX2`, `multX1`, `multX0_5` du preset Rainbow DOWN de l'Affectation, arrondi par défaut au centime. Cash lu par `RealPortfolioSource` (illisible ou nul ⇒ pas de proposition). Le montant est coté via `BindingPathQuoteService` : `BELOW_MIN`, niveau Fee Test et avertissements remontés ; devis indisponible ⇒ proposition gardée avec avertissement. Bande proposée : neutre (`ModulationDefaults`), aucun profil utilisateur n'existe.
- **Écran** : page `/app/onboarding` (cf. [`11-front-app.md`](11-front-app.md)). Le déclenchement est manuel : la sauvegarde d'une clé TRADE ne lie rien toute seule.
- Tests : `RainbowLiveOnboardingServiceTest`.

### Écrans de modulation

- **Admin, onglet « Modulation »** (`fragments/admin/modulation.html`, `assets/js/admin/modulation.js`) : un champ numérique par paramètre global (défaut et bornes absolues affichés), « Enregistrer » et « Remettre les défauts » via `GET/PUT /api/admin/rainbow-modulation` ; refus serveur affiché dans le bandeau d'alerte. ## Profils de départ et historique de la modulation

- `StartingProfile` : `PRUDENT` 20–50, `BALANCED` 30–70, `DYNAMIC` 40–90, `FULL` 0–100, `CUSTOM` (non sélectionnable : état atteint par modification manuelle).
- `UserModulationService` (seul point d'écriture de la modulation côté utilisateur) : `update(...)` valide via `UserTradingSettingsService`, et si les valeurs changent réellement bascule le profil sur `CUSTOM` et journalise (`MANUAL`) ; `applyProfile(profile)` ne remplace que la bande (puissance, biais, marge conservés), refuse `null`/`CUSTOM`, journalise (`PROFILE`) si la bande change ; `history(user)` = 50 derniers changements.
- Historique : table `user_modulation_history` (user, `occurred_at`, `source` PROFILE|MANUAL, profil avant/après, valeurs avant/après `before_*`/`after_*` : exposition min/max, puissance, biais, marge ; `ON DELETE CASCADE`). Lecture : `GET /api/user/modulation-settings/history`.
