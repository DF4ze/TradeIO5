# Rainbow DCA ATR live — presets, signal quotidien, liens (bindings), API REST

Vérifié le : 2026-10-13 (`service/market/instrument/*`, `service/connector/{instrument,fee,orderbook}`, `service/dca/atr/binding/BindingPathQuoteService`, `model/entity/dca/bench/*`, `repository/dca/bench/*`, `service/dca/atr/bench/{RainbowLivePresetService,RainbowAssetStrategyService,RainbowLiveRunService,RainbowLiveBindingRunService,RainbowLiveExecutionService,RainbowTrendLiveService,RainbowLiveQueryService,RainbowLiveDefaultPresets,RealPortfolioSource,LiveSizing,CashLedger}`, `model/dto/dca/bench/RainbowLiveDtos`, `service/scheduler/RainbowLivePass2355Job`, `configuration/initializer/RainbowAssetStrategyInitializer`, `controller/RainbowLive{,Admin}Controller`, `controller/RainbowLiveControllerAdvice`, `templates/userPage.html`, `templates/fragments/rainbowLive.html`, `static/assets/js/rainbow-live.js`, `static/assets/css/rainbow-live.css`).

Périmètre : persistance + moteur câblé + **une passe quotidienne à 23:55 UTC** (job désactivé par défaut) + déclenchement admin + API REST utilisateur (CRUD presets, activation, liens, wallet réel) + page web dans `/user` (section « Presets — Rainbow DCA ATR »). La passe calcule le **signal** de chaque preset actif, le dimensionne sur le **portefeuille réel en lecture seule** (par lien) et alimente le plan d'ordres ([`10-execution-plan.md`](10-execution-plan.md)). Aucun appel exchange hors lecture de marché, lecture des soldes (`RealPortfolioSource`) et exécution réelle verrouillée (test de garde `RainbowLiveNoExchangeDependencyTest`). Le moteur pur reste `service/dca/atr/RainbowAtrEngine` (cf. [`04-market-data.md`](04-market-data.md)).

Il n'existe **aucun wallet fictif ni performance simulée** : le signal d'un preset n'est jamais plafonné par un portefeuille, seul le dimensionnement par lien (portefeuille réel) l'est.

## Entités (schéma créé par `ddl-auto=update` ; migration Flyway préparée mais non activée, cf. [`../operations/flyway.md`](../operations/flyway.md))

- `RainbowLivePreset` (`rainbow_live_preset`) : `user` (FK `User`), `assetSymbol` (BTC|ETH|PAXG), `name`, `enabled`, `analysisWindowMonths`, `assetStrategy` (FK nullable vers `RainbowAssetStrategy`, colonne `asset_strategy_id` : le preset **suit** la stratégie Actif ⇒ non modifiable, non supprimable, config lue dans la stratégie à chaque passe ; nul = preset propre au user), `createdAt`/`updatedAt`, + `@Embedded RainbowAtrConfig`. **Unique (user, asset_symbol, name)**. Timeframe 1D fixe (non stocké). `enabled` = activation par l'utilisateur : seul un preset actif est joué par la passe (bascule `PATCH /presets/{id}/enabled`).
- `RainbowAtrConfig` (`@Embeddable`) : 1 colonne typée par paramètre = `RainbowAtrTuning` (17) + `RainbowAtrGlobals` (12 + `multX2/X1/X0_5/Triggered` + `baseAmount`). `of(tuning, globals)`, `toTuning()`, `toGlobals()`, `hash()` (SHA-256 tronqué). `baseAmount` n'existe que dans la config. Réutilisé tel quel (mêmes noms de colonnes) comme snapshot dans le run.
- `RainbowAssetStrategy` (`rainbow_asset_strategy`) — **Stratégie Actif**, pilotée par le compte System : une par actif (« TrendMix Rainbow DCA ATR · BTC|ETH|PAXG »), sans user ni run : `assetSymbol`, `name`, `mode`, `analysisWindowMonths`, `@Embedded RainbowAtrConfig` (instantané du jeu Bear), `trendConfigJson` (`TrendConfigDto` sérialisé, null si FIXED), `revision` (1 à la création, +1 à chaque modification), `createdAt`/`updatedAt`. **Unique (asset_symbol, name)**. Modifiable (`RainbowAssetStrategyService#update`, endpoint admin), jamais supprimable (`@PreRemove` lève une exception). Créée par `RainbowAssetStrategyInitializer` si absente, **jamais écrasée** ; le catalogue du code (`RainbowAssetStrategyService#catalog`) ne sert que de graine. Seules les stratégies TrendMix sont fournies (un user peut créer des presets FIXED à la main).
- `RainbowLivePresetEvent` (`rainbow_live_preset_event`) : historique des switchs de preset d'un user (`type` ENABLE | DISABLE | DETACH | LIVE_SWITCH | STRATEGY_CHANGED, `assetSymbol`, id + nom du preset avant/après sans FK, `strategyRevision`, `occurredAt` via `DomainClock`, `reason`), `ON DELETE CASCADE` sur le user. Écrit par `RainbowLivePresetEventService` : activation/désactivation effective, détachement, création/bascule d'un binding (`LIVE_SWITCH`), et `STRATEGY_CHANGED` à la 1re passe qui constate une nouvelle révision (une fois par preset et révision).
- `RainbowLivePreset.mode` (`RainbowLiveMode`, nullable = `FIXED`) : `FIXED` (un jeu de paramètres, rejeu de la fenêtre à chaque passe) ou `TREND_MIX` (jeu Bull/Bear choisi chaque jour par la Trend Mix, état persisté).
- `RainbowLiveTrendConfig` (`rainbow_live_trend_config`) : 1-1 avec un preset `TREND_MIX` (`ON DELETE CASCADE`) : paramètres du Trend Mix (colonnes typées), `rangeMapping` (`KEEP_PREVIOUS|TO_BEAR|TO_BULL`) et les jeux Bear/Bull (`bearJson`/`bullJson` = `{tuning, globals}`). Absente ⇒ défauts du code (`RainbowLiveTrendConfigs#defaults`).
- `RainbowLiveUserSettings` (`rainbow_live_user_settings`) : une ligne par user, `uiMode` (`RainbowLiveUiMode` AUTO|SIMPLE|ADVANCED|EXPERT ; absente ⇒ `EXPERT`).
- `RainbowLiveEngineState` (`rainbow_live_engine_state`) : unique (preset, `state_day`), `ON DELETE CASCADE` ; état de la machine Rainbow du Trend Mix (`RainbowAtrState` : armements, verrou, cooldown, réserve moon, automate moon) + **`positionQty`** (position VIRTUELLE du moteur, base de la réserve moon et des ventes, indépendante de tout wallet) + `configHash` (empreinte de la config effective : fenêtre + jeux Bear/Bull + réglages Trend, ou jeu FIXED) à la FIN du jour. NaN stockés `null`.
- `RainbowAthReference` (`rainbow_ath_reference`) : unique (actif, `ref_day`) ; ATH par ACTIF valable à la fin du jour (une ligne par jour : le run du lendemain relit l'ATH de la veille).
- `RainbowLiveBinding` (`rainbow_live_binding`) : lien (user, actif, wallet) → **preset** + **wallet réel** (lecture seule). **Unique (`user_id`, `asset_symbol`, `wallet_id`)** (`uk_rainbow_live_binding_user_asset_wallet`) ⇒ un binding par actif **et par wallet**. Un preset peut alimenter plusieurs bindings (`findAllByPreset`). Champs : `preset` (FK, doit appartenir au user et à l'actif), `wallet` (FK `Wallet`, doit appartenir au user), `bagPercent` (0-100, défaut 100, part **dynamique** de la position réelle offerte à la stratégie), `priority` (ordre de passage du cash, défaut = rang dans `RainbowLiveDefaultPresets.ASSETS` : BTC 0, ETH 1, PAXG 2). Un preset lié ne peut pas être supprimé (400). Donnée utilisateur créée par l'API, jamais par un initializer. Lu par le moteur via `RealPortfolioSource.read(binding)`.
- `RainbowLiveRun` (`rainbow_live_run`) : **unique (preset, `run_day`)**, `ON DELETE CASCADE` sur le preset ; `user`, `assetSymbol`, `day` (jour UTC), un bloc `@Embedded RainbowLivePassBlock signal` (colonnes `signal_*`), `config` (snapshot) + `configHash`. Signal **par preset**, non plafonné.
- `RainbowLivePassBlock` : `close`, `sma`, `atr`, `boundDown2`/`boundDown1`/`boundUp1`/`boundUp2`/`boundUp3` (SMA ± ATR×mult correspondant), `zone`, `athDistance`, `buyFactor`/`sellFactor`, `moonMode`, `buyArmed`/`sellArmed`/`buyLocked`, `cooldownRemaining`, `moonReserveQty`, `activeSet` (ex. « BTC Perso Bull ») et `trendRegime` (UP/DOWN/RANGE) pour le Trend Mix, action décidée (`RainbowLiveAction` BUY/SELL/NONE, `actionAmountUsdc`, `actionQuantity`, `actionPrice`), `configHash`, `computedAt`.
- `RainbowLiveBindingRun` (`rainbow_live_binding_run`) : **unique (binding, `run_day`)**, `ON DELETE CASCADE` sur le binding ; snapshot live **par lien** : un bloc `@Embedded RainbowLiveLiveBlock live` (colonnes `live_*`), `computedAt`.
- `RainbowLiveLiveBlock` : `status` (`PortfolioStatus` OK|UNAVAILABLE|NOT_TRADABLE), `walletId`, `fetchedAt`, `cashUsd`, `cashDetail` (JSON par membre du groupe USD), `positionQty`, `tradableQty`, `cashReserved` (déjà consommé par les actifs servis avant), `blockReason` (`NONE|INSUFFICIENT_CASH|NOT_TRADABLE_WITHOUT_FIAT|UNAVAILABLE`), `actionType` (`BUY|SELL|NONE|BLOCKED`), `actionAmountUsdc`, `actionQuantity`, `candleSource` (exchange réel des candles du signal du lien), `candleSourceSubstituted`.

Suppression d'un preset ⇒ runs supprimés par FK. Édition d'un preset ⇒ même id et historique conservés, aucun run écrit ni recalculé.

## Sémantique du run (`RainbowLiveRunService`)

Horloge `DomainClock` (`computedAt`) ; un run par (preset, jour UTC).
- **`upsert(preset, day, block)`** (passe du jour, 23:55 UTC) : crée le run ou, sur rejeu du même jour, remplace les indicateurs en **conservant l'action d'origine**.
- **`refresh(preset, day, closedBlock)`** (passe du lendemain) : remplace les indicateurs d'un run existant par ceux calculés sur la bougie désormais **clôturée** ; l'action décidée à 23:55 reste figée. Sans run ce jour-là : `false`, rien n'est écrit (pas de rattrapage). `hasSignal(preset, day)` conditionne le rafraîchissement.
- Chaque écriture rafraîchit le snapshot de config du run et le hash (aussi stocké dans le bloc) ; comparer au hash du preset détecte « config modifiée ».
- `RainbowLiveBindingRunService` : `snapshotOf(binding, day)` / `upsert(binding, day, block)` ; rejeu du même jour : snapshot live existant conservé.

## Presets (`RainbowLivePresetService`)

`create` (valide `Tuning.isValid()`, fenêtre ≥ 1, baseAmount > 0, actif autorisé, nom libre), `update` (nom, enabled, fenêtre, config ; actif non modifiable), `delete`, `get(user, id)`, `list(user[, actif])` ; opérations réservées au propriétaire. Erreurs typées (sous-classes d'`IllegalArgumentException`) : `RainbowLivePresetNotFoundException` (inexistant **ou** d'un autre user), `RainbowLivePresetConflictException` (nom déjà pris pour l'actif).

**Stratégie Actif et presets qui la suivent** : `RainbowAssetStrategyInitializer` (`@Order(60)`, au démarrage) insère les stratégies absentes du catalogue (une « Trend Mix » par actif, réglages par défaut du code) et ne modifie jamais une stratégie existante ; System la modifie ensuite en base (`PUT /api/admin/rainbow-live/strategies/{id}`, fenêtre + réglages Trend dont jeux Bear/Bull, validations de `RainbowLiveTrendConfigs#normalize` ; `revision` + 1). `ensureStrategyPresets(User)` (appelé par la passe quotidienne et par `GET /presets`) crée, pour chaque stratégie dont le user n'a pas le preset, un preset qui la **suit** : nom = `SYSTEM_PREFIX` (« [Système] ») + nom de la stratégie, `assetStrategy` renseignée, **inactif** (`enabled=false`), runs propres, **aucune copie de config ni ligne Trend**. Jamais recréé ni modifié. Sur un preset qui suit, `update` et `delete` lèvent `RainbowLivePresetFollowsStrategyException` (409) ; seul `setEnabled` (`PATCH /presets/{id}/enabled`) est permis. Le préfixe est réservé : refusé (400) sur un preset créé ou renommé par l'utilisateur.

**Config effective** (`RainbowLivePresetConfigResolver`) : accesseur unique de la config d'un preset (`config`, `analysisWindowMonths`, `trendConfig`, `effectiveHash`) = celle de la stratégie suivie (lue à chaque appel) ou, pour un preset propre, ses colonnes / sa ligne `RainbowLiveTrendConfig`. Un changement de la stratégie s'applique à la passe suivante chez tous les users qui la suivent, sans toucher aux détachés.

**Détachement** : dupliquer un preset qui suit une stratégie (`POST /presets` avec `duplicatedFromId`) crée un preset propre (`assetStrategy` nulle, réglages copiés dans sa propre ligne) ; l'ancien preset garde ses runs et son état. Événement `DETACH` (révision suivie). La page affiche un avertissement avant la duplication d'un preset qui suit.

## Passe quotidienne (`RainbowLiveExecutionService#runPass(asOf[, dayOverride])`)

Une seule passe par jour, à **23:55 UTC**, sur la bougie D1 **du jour encore ouverte** (valeurs provisoires), comptabilisée sur le **jour UTC courant** (`dayFor(asOf)` = date UTC de `asOf`) : le signal tombe sur la bougie du jour affichée par l'exchange. Horloge injectée (`DomainClock` dans le job/l'endpoint, `asOf` explicite en test) ; `synchronized` (cron et déclenchement manuel ne se chevauchent pas). `dayOverride` (endpoint) force le jour.

- **Utilisateurs/presets** : pour chaque `User` `enabled` non archivé, `ensureStrategyPresets` puis presets `enabled` groupés par actif. Clé user jamais codée en dur. Une erreur (user, actif, preset) est comptée et n'arrête jamais les autres ; pas de rattrapage des jours manqués.
- **Données** : `MarketDatasetEngine.getDailyDatasetForAsset(actif, D1_LOOKBACK_CANDLES, asOf, source)` — chemin D1 **natif** (hors Bucket H1, cf. [`04-market-data.md`](04-market-data.md#chemin-d1-natif-rainbow-getdailydatasetforasset)), chargé **une fois par (actif, source, passe)** et partagé entre presets/users. `source` = exchange du wallet du lien (`LiveCandleSource`, `null` si wallet sans exchange de marché : défauts `asset_provider`). La bougie du `day` est repérée par sa date UTC ; la bougie du jour suivant, éventuelle, est ignorée ; bougie absente ⇒ WARN, série sautée (pas d'exception). Dataset < warmup+2 ⇒ preset sauté.
- **Rafraîchissement J-1** (`refreshPreviousDay`, avant le run du jour) : si le preset a un run la veille, il est rejoué sur la série tronquée à J-1 (bougie désormais clôturée) : indicateurs, et pour le Trend Mix état moteur + position virtuelle + ATH (`Outcome#commit` seulement si le run existait). **L'action décidée la veille reste figée.** Une erreur ici est un WARN et n'empêche pas le run du jour.
- **Signal par lien** : le preset est calculé sur la source de son lien le plus prioritaire qui a un exchange (défauts sans lien). Chaque lien d'un preset **ATR (FIXED)** sur une AUTRE source rejoue le moteur sur la série de cette source (`replayAtr`, sans état) ; un preset `TREND_MIX` (machine d'état unique) partage son signal entre ses liens, avec WARN si les sources diffèrent (lien marqué substitué). Source indisponible ⇒ fallback `asset_provider` avec WARN bruyant ; le snapshot du lien porte `candleSource` et `candleSourceSubstituted`.
- **Fenêtre** : `RainbowLiveDefaultPresets.D1_LOOKBACK_CANDLES` = **720** (limite native Kraken `OHLC` D1, test de garde). L'ATH du moteur (mode FIXED) est le plus haut de ces 720 j ; un actif sans ATH depuis 720 j est considéré mort. Voir [`../known-gaps/rainbow-dca-chantiers-ouverts.md`](../known-gaps/rainbow-dca-chantiers-ouverts.md).
- **Rejeu FIXED** : `startIdx = max(warmup(sma, atr), 1re bougie ≥ day − analysisWindowMonths)`, `endIdx` = bougie du jour ; `RainbowAtrEngine.simulate(..., trace=true)` (moteur inchangé).
- **Action du jour** = events dont `index == endIdx` : `BUY_ZONE`/`BUY_TRIGGERED` ⇒ BUY (montant moteur en USDC), `SELL`/`MOON_STOP` ⇒ SELL (quantités sommées). Achat et vente sur la même bougie : la **vente l'emporte** (WARN). Le signal n'est **plafonné par aucun portefeuille** (`applyWanted`) ; il est transmis en `LiveDemand` (achat voulu, vente = quantité moteur ou fraction × position tradable) puis dimensionné par lien.
- **Persistance** : bloc `RainbowLivePassBlock` complet via `RainbowLiveRunService#upsert`. Retour : `PassSummary(day, processed, skipped, errors)`.

## Dimensionnement sur le portefeuille réel (par lien)

Un preset lié par au moins un binding est dimensionné, **une fois par lien**, sur le portefeuille réel en LECTURE SEULE (aucun ordre). Un preset sans lien produit son signal (run) mais aucun run de lien.
- **Port** `RainbowPortfolioSource` : `liveSlots(user)` (`LiveSlot(bindingId, presetId, assetSymbol, walletId, priority, bagPercent, candleSource)` triés par `priority`). Implémentation `RealPortfolioSource` (seul bean du bench à toucher l'exchange) : `read(binding)` → `PortfolioReading(cash USD, cashByMember, positions, fetchedAt, status OK|UNAVAILABLE|NOT_TRADABLE, walletId)` ; `BindingCheck` à chaque passe, puis soldes disponibles via `ReadOnlyBalanceReader`, cache 60 s. Périmètre BTC/ETH/PAXG + membres du groupe `USD` (cash = USDC, détail par membre conservé ; le stock en transit actif est déduit de la position du lien portant la même devise), autres soldes ignorés. Panne, clé rejetée, binding KO, lecture sans aucun solde du périmètre ⇒ `UNAVAILABLE` (jamais un 0 silencieux). `NOT_TRADABLE_WITHOUT_FIAT` ⇒ `NOT_TRADABLE` (soldes non lus, aucune action). Chaque `BindingCheck` persiste `tradability`, `quoteMember`, `routeKey`, `tradabilityCheckedAt` sur le binding ; `ExecutionGuard.requireExecutable(binding)` est le point de passage obligatoire de l'exécution (refus si le statut persisté n'est pas `OK`).
- **Ordre et cash commun** (`CashLedger`) : par utilisateur, liens d'abord par `priority` croissante (puis rang d'actif, puis `bindingId`), un ledger par wallet (pool USD = USDC créé à la première lecture OK). Achat accepté ⇒ cash réservé ; achat > cash restant ⇒ **tout-ou-rien**, action `BLOCKED` + `INSUFFICIENT_CASH`. Les ventes ne sont pas créditées le jour même.
- **Position tradable** = `bagPercent`/100 × position réelle (dynamique) ; vente plafonnée à la position tradable (`LiveSizing`). Achat et vente le même jour : la vente l'emporte.
- **Snapshot par lien** (`RainbowLiveBindingRun`) : voir `RainbowLiveLiveBlock`. Une panne d'un lien n'affecte pas les autres. `UNAVAILABLE` ⇒ `NONE` + raison `UNAVAILABLE`, WARN.
- **Rejeu du même jour** : snapshot et action live d'origine conservés ; un achat d'origine reste réservé dans le pool (pas de nouvelle lecture exchange). Le lendemain, une nouvelle lecture est faite pour le nouveau jour ; le snapshot de la veille n'est pas modifié.
- **Garde** `RainbowLiveNoExchangeDependencyTest` : seules les implémentations de `RainbowPortfolioSource` peuvent dépendre de `service.connector`/`Wallet`/`ProviderApiService` dans le package du bench ; le port n'a aucune méthode d'ordre.

## Presets `TREND_MIX` (`RainbowTrendLiveService`)

Mêmes runs, même job et même passe que le mode `FIXED`. Pour un preset `TREND_MIX`, `RainbowLiveExecutionService` délègue à `RainbowTrendLiveService#run(day, preset, candles, dataset, dayIdx)` :

1. **Trend** : `TrendMixCalculator` (réglages du preset, cf. [`09-trend.md`](09-trend.md)) sur la série D1 chargée, puis `RainbowSetSelector` (RANGE selon `rangeMapping`, Bear au départ) → jeu Bear/Bull du preset (`RainbowLiveTrendConfigs#resolve` : ligne `RainbowLiveTrendConfig`, sinon `RainbowAtrPresets.bearBull`). Le montant de base est celui du jeu actif. Les runs écrits restent figés (snapshot de config + `configHash` par run).
2. **État et position virtuelle** : dernière ligne `RainbowLiveEngineState` antérieure au jour **si son `configHash` == `RainbowLivePresetConfigResolver#effectiveHash`**. Absente (1re passe) ou hash différent (réglage propre modifié, révision de la stratégie suivie) ⇒ (ré-)amorçage par `RainbowAtrReplay.runFull` sur `analysisWindowMonths` mois jusqu'à la veille avec la config courante (état + `finalPosition()`), enregistré pour la veille. Un ré-amorçage d'un preset qui suit écrit `STRATEGY_CHANGED` (une fois par preset et révision). Hors changement, l'état est recalculé depuis celui de la veille (un seul `RainbowAtrStrategy#step`).
3. **ATH** : `RainbowAthService#athBefore` (ATH de la veille, lu en base). Amorçage one-shot à la 1re demande d'un actif sans aucune ligne : historique D1 complet Binance (`BinanceDailyCandleFetcher`, klines publics, seul appel exchange hors portefeuille, une fois par actif).
4. **Dimensionnement du signal** : `ReferenceSizer` (base × facteur ATH × multiplicateur de zone ; vente = fraction × position **virtuelle**), sans plafond de portefeuille.
5. **Écritures** : état du jour, position virtuelle (`max(0, position − quantité vendue + montant acheté / close)`) et ATH du jour via `Outcome#commit`, après l'enregistrement du run. Le run du lendemain rejoue le jour sur la vraie clôture (même chemin) et **remplace** ces écritures. Rejouer une passe est idempotent.

Création / édition : `POST /presets` avec `mode=TREND_MIX` + `trendConfig` (parties absentes ⇒ défauts de l'actif), `PUT` avec `trendConfig` (absent ⇒ inchangé) ; validation `RainbowLiveTrendConfigs#validate` (fenêtres ≥ 2, `0 ≤ exit ≤ enter`, `confirm ≥ 1`, tunings valides, `baseAmount > 0`). La config embarquée du preset recopie le jeu Bear (instantané informatif).

## Job et déclenchement manuel

`RainbowLivePass2355Job` : propriété `tradeio.rainbow-live.pass-2355-cron`, défaut `-` (désactivé), `zone = "UTC"` explicite, cron cible `0 55 23 * * *` (cf. [`operations/scheduled-jobs.md`](../operations/scheduled-jobs.md)). Manuel : `POST /api/admin/rainbow-live/run[?day=YYYY-MM-DD]` (ADMIN, `RainbowLiveAdminController`, réponse = `PassSummary`). Pas de déclenchement manuel côté user.

**Instantané de patrimoine** (`PortfolioSnapshotService`, `portfolio_snapshot` + `portfolio_snapshot_asset`) : en fin de passe, une ligne **immuable** par (user, wallet, jour UTC) : statut de la lecture, stable (`cashUsd`), valeur des actifs, patrimoine, exposition %, bande d'exposition de l'utilisateur en vigueur (`exposureMin/Max`), base de prix `D1_OPEN_2355` (clôture de la bougie D1 encore ouverte, la même que le signal) ; une ligne d'actif (quantité, prix, valeur) par actif détenu ou lié. Réutilise la **lecture de la passe** (aucun appel exchange en plus) : pas de lecture ⇒ pas d'instantané. Lecture non `OK` ⇒ statut conservé, valeurs nulles (jamais 0) ; prix manquant pour un actif détenu ⇒ totaux et exposition nuls. Idempotent (unicité user/wallet/jour : un rejeu ne réécrit rien), pas de rattrapage ni de reconstruction rétroactive ; le provider se déduit de `wallet.exchange`. Lecture : `PortfolioSnapshotRepository` (aucun endpoint encore, cf. [`../graphique/inventaire-options-affichage.md`](../graphique/inventaire-options-affichage.md) §6).

## API REST utilisateur (`RainbowLiveController`, `/api/rainbow-live`)

Contrat détaillé : [`../api/rest-endpoints.md`](../api/rest-endpoints.md). `@PreAuthorize("isAuthenticated()")` au niveau classe ; utilisateur = `IAuthenticationFacade#getConnectedUser()` ; tout est scopé à l'user connecté (aucune clé user en dur), preset d'un autre user ou inexistant ⇒ 404. DTO dédiés (`RainbowLiveDtos`, jamais d'entité JPA) ; `tuning`/`globals` = records `RainbowAtrTuning`/`RainbowAtrGlobals` tels quels. Erreurs : `RainbowLiveControllerAdvice` (limité à ce contrôleur) ⇒ `IllegalArgumentException` 400, not found 404, conflit de nom 409. Lectures via `RainbowLiveQueryService` (`@Transactional(readOnly)`, agrégats presets en requêtes groupées) ; `listPresets` est en écriture (copie des presets de stratégie).

## Bindings et vérification de disponibilité (`service/dca/atr/binding/`)

- `RainbowLiveBindingService` : CRUD scopé au user (binding, preset ou wallet d'un autre user ⇒ `RainbowLiveBindingNotFoundException`/`RainbowLivePresetNotFoundException` ⇒ 404 ; binding déjà existant pour (actif, wallet) ⇒ 409 ; mauvais actif de preset, `bagPercent` hors [0,100], actif inconnu ⇒ 400). Création et modification retournent le résultat de `BindingCheck` sans le persister : un KO n'empêche pas l'enregistrement.
- `BindingCheck` (appelable depuis le moteur) → `BindingCheckResult(status, message, quoteMember, routeKey)` (`isOk()` = OK ou TRADABLE_VIA_INTERMEDIARY : lecture autorisée ; `isExecutable()` = OK seul, tant que l'exécution multi-jambes n'existe pas ; `isBlocked()` = NOT_TRADABLE_WITHOUT_FIAT), jamais d'exception métier. Ordre : wallet activé (`WALLET_DISABLED`) → credential active (`CREDENTIAL_INVALID`) → lecteur + vérificateur pour l'exchange (`PROVIDER_UNSUPPORTED`) → lecture des soldes via `ReadOnlyBalanceReader` (`CredentialRejectedException` = clé/signature/passphrase/permission/IP rejetées ⇒ `CREDENTIAL_INVALID` ; autre panne ⇒ `BALANCE_UNAVAILABLE`) → chemin spot **sans monnaie fiat** (USDC, catalogue en base) : paire `<actif>/USDC` ⇒ `OK` ; sinon route via un intermédiaire choisi (BTC, `PathFinder`) ⇒ `TRADABLE_VIA_INTERMEDIARY` (`quoteMember`, `routeKey` ex. `USDC>BTC>PAXG`, mémorisée sur le lien) ; sinon `NOT_TRADABLE_WITHOUT_FIAT` ; catalogue absent et exchange injoignable ⇒ `INSTRUMENT_UNAVAILABLE`. Solde nul accepté, clé absente de la map = solde 0 (pas indisponible) ; les soldes ne sont ni conservés ni exposés.
- **Catalogue d'instruments** (`service/market/instrument/InstrumentCatalog`, table `exchange_instrument` : provider, `inst_id` `BASE-QUOTE` normalisé, base, quote, `state`, `min_sz`, `lot_sz`, `tick_sz`, `cost_min` (nullable ; Kraken `costmin`), `native_pair` (nullable ; Kraken `altname`), `fee_currency` (nullable ; Kraken `fee_volume_currency`), `fetched_at`, unique (provider, inst_id)) : lu par `BindingCheck` et `PathFinder`. Alimenté par **un seul** appel public « toutes les paires » par exchange via `InstrumentListClient` (`OkxInstrumentListClient` : `GET /api/v5/public/instruments?instType=SPOT`, `state=live` ; `KrakenInstrumentListClient` : `GET /0/public/AssetPairs`, noms normalisés par `KrakenAssetNames`, `status=online`, paires `.d` ignorées). Rafraîchi à la demande quand il a plus de 24 h (`tradeio.execution.instrument-catalog.refresh-after`, défaut `PT24H`) ou via `refresh(provider)` ; panne ⇒ catalogue conservé (WARN), jamais vidé, pas de nouvelle tentative avant 5 min ; catalogue absent et exchange injoignable ⇒ `InstrumentLookupException` ⇒ `INSTRUMENT_UNAVAILABLE`. Pas de checker Binance (pas de wallet Binance).
- `WalletInitializer` ne crée plus de wallet Binance ; il crée le wallet « OKX » (credential OKX si présente) en plus de Kraken/Binance Test/Ledger. Les lignes déjà en base ne sont pas touchées.

## Chemin d'achat chiffré : frais, carnet, PathFinder, Fee Test (lecture seule, aucun ordre)

Calcul **à la demande** (`GET /api/rainbow-live/bindings/{id}/path-quote?amount=`, cf. [`../api/rest-endpoints.md`](../api/rest-endpoints.md)) ; aucun job, aucune écriture hors cache du catalogue. `BindingPathQuoteService` (`service/dca/atr/binding`) : binding du user (sinon 404) → soldes du wallet (`ReadOnlyBalanceReader`) filtrés sur les membres du groupe `USD` (sources) → catalogue → `PathFinder` avec un marché réel (`LegMarketSource`).
- **Frais réels** : `TradingFeeProvider` / `OkxTradingFeeProvider` (`GET /api/v5/account/trade-fee?instType=SPOT&instId=…`, clé Read du wallet, signature HMAC partagée avec `OkxBalanceReader` dans `OkxSignedRequests`). Taux OKX signés (négatif = frais payé) normalisés en `FeeRate(makerPct, takerPct)` en % (positif = coût) ; champs `maker/taker` pour les paires USDT, `makerUSDC/takerUSDC` pour les paires USDC ; champ absent ⇒ `BalanceUnavailableException` (jamais de frais supposé). Cache mémoire 24 h sur `DomainClock` (échecs non cachés), throttle 500 ms entre appels réseau. Compte OKX de Clem (EEA, niveau « Utilisateur régulier ») : 0,10 % maker / 0,20 % taker, 0 % sur `USDC-USDT`. Le coût d'une jambe utilise le taux **taker** (ordres limit IOC prévus). Clé rejetée (50100-50114) ⇒ `CredentialRejectedException`.
- **Frais réels Kraken** : `KrakenTradingFeeProvider` (`POST /0/private/TradeVolume` `pair=<nativePair>&fee-info=true`, clé Read, signature `KrakenSignedRequests`). `fees` = taker, `fees_maker` = maker, déjà en % ; champ absent ⇒ `BalanceUnavailableException`. Cache 24 h par (clé, instrument), échecs non cachés, throttle 1 s.
- **Carnet public** : `OrderBookClient` / `OkxOrderBookClient` (`GET /api/v5/market/books?instId=&sz=50` → `OrderBookSnapshot`) ; repli `GET /api/v5/market/ticker` (un niveau par côté) marqué `estimation=TICKER` (slippage non chiffré). Un appel par devis, pas de cache. Kraken : `KrakenOrderBookClient` (`GET /0/public/Depth?pair=<nativePair>&count=`, repli `/0/public/Ticker` marqué `TICKER`), paire lue au catalogue (`nativePair`, repli `KrakenAssetNames.fallbackPair`) ; le catalogue expose des `inst_id` en symboles standard (`KrakenAssetNames`).
- **`PathFinder`** (`service/market/instrument`, pur) : arêtes BUY `QUOTE→BASE` (ask) et SELL `BASE→QUOTE` (bid) pour chaque paire du catalogue ; paires touchant un nœud interdit ignorées (fiat : `ExecutionDefaults.FIAT_CURRENCIES` ; `USDT` ; surcharge `tradeio.execution.forbidden-nodes`, liste CSV) ; sources = devises détenues ; profondeur ≤ `MAX_PATH_DEPTH` (2), énumération exhaustive. Intermédiaires autorisés `ExecutionDefaults.INTERMEDIARIES` (BTC, ETH), choisis automatiquement `CHOSEN_INTERMEDIARIES` (BTC seul) : une route ETH est chiffrée et exposée (`chosen=false`), jamais retenue. Coût d'une jambe = frais taker + demi-spread + slippage au montant (VWAP du carnet, `BookSlippage`) ; route = **somme brute**. Jambes dimensionnées en séquence sur le **net reçu** de la précédente ; `sz` ⌊⌋ au `lotSz` en BUY, ⌈⌉ en SELL, `minSz`/`costMin` ⇒ `BELOW_MIN`. Résultat `PathQuote(status OK|NO_PATH|BELOW_MIN, source, legs[], totalCostPct, feeTestLevel, estimation BOOK|TICKER, underfunded, routeKey, routes[RouteQuote])` ; `NO_PATH` ⇒ « non tradable sans monnaie fiat ». Vente : route vers USDC (`X>USDC` ou `X>BTC>USDC`).
- **`FeeTest`** (pur) : coût total < `warn-pct` ⇒ GREEN ; de `warn` à `red` **inclus** ⇒ WARNING ; > `red` ⇒ RED. Propriétés `tradeio.execution.fee-test.warn-pct` (défaut 0,2) et `red-pct` (0,8), défauts en constantes (`ExecutionDefaults`). Pourcentages exposés en %, jamais en bps.
- Gardes : `ConnectorNoOrderMethodTest` et `RainbowLiveNoExchangeDependencyTest` ; aucune méthode d'ordre dans ces chemins.

## Groupes d'actifs (USD = USDC)

- Tables `asset_group` (`code` unique, `valuation` = `NOMINAL`) et `asset_group_member` (`asset_id` **unique** : un actif dans un seul groupe, `position` = ordre de préférence, 0 = membre de cotation privilégié). `AssetGroupInitializer` (`@Order(2)`, après `AssetInitializer`) sème `USD` = USDC (0), idempotent (USDT exclu partout, `ExecutionDefaults.EXCLUDED_STABLE`), jamais écrasé. Code `USD` défini une seule fois : `AssetGroup.USD`.
- `AssetGroupService` : `groupBySymbol()`, `members(code)`, `byMember(code, soldes)`. Valorisation **nominale** (1 membre = 1 unité du groupe, écart de peg ignoré, aucun appel de prix).
- Home (`AssetOverviewService`) : les membres d'un groupe (et leurs `LD*` Binance) sont agrégés en une ligne au code du groupe (« USD »), prix 1. Le fiat `USD` (ZUSD Kraken) est ignoré pour ne pas fusionner avec le groupe.
- Wallet réel : le cash est `Σ` des soldes des membres (`cashUsd`, détail `cashByMember` persisté en JSON dans `cash_detail` du bloc live). USDT est ignoré (hors périmètre).

## Modulation : paramètres admin et réglages utilisateur

**Principe : le Rainbow reste seul à acheter et vendre ; la modulation ne fait que changer les quantités qu'il demande** (aucun ordre de rééquilibrage). Signal (`LiveDemand`) et plan d'ordres inchangés : seul `LiveSizing` module, par lien. Roadmap : [`../prompts/prompt-roadmap-modulation-bande-puissance.md`](../prompts/prompt-roadmap-modulation-bande-puissance.md).

- **Constantes** : `service/modulation/ModulationDefaults` (défaut + bornes absolues incluses de chaque paramètre admin, valeurs neutres utilisateur 0 / 100 / 1 / 0) ; la base ne relève jamais une borne absolue.
- **Paramètres admin globaux** : singleton `RainbowModulationControl` (`rainbow_modulation_control`, id 1, `updatedAt`, `updatedBy`) : `regulationMarginPct` (25, 5–50), `sellBoostMax` (2, 1–4), `biasMax` (0,5, 0–1), `powerMin`/`powerMax` (0,25/2, 0–3), `minBandWidthPts` (10, 5–50), `modulationProductMax` (2,5, 1–5), `autonomyDays` (90, 7–365). `RainbowModulationControlService.current()` relit la base à chaque appel (sans cache), ligne absente ⇒ défauts ; `update(Params, by)` valide chaque borne et impose `powerMin ≤ 1 ≤ powerMax` (`IllegalArgumentException`, rien écrit). `RainbowModulationControlInitializer` (`@Order(71)`) crée la ligne si absente, ne modifie jamais une ligne existante.
- **Journal** : `AdminModulationService` écrit une ligne `AdminAction.MODULATION` (`target = rainbow-modulation`, payload `{before, after}`; `REFUSED` si invalide).
- **Réglages utilisateur** : `UserTradingSettings.exposureMin|exposureMax|power|bias` (`Double` **nullables** : null ⇒ neutre 0 / 100 / 1 / 0). `UserTradingSettingsService` : `getModulationSettings` (stocké ou neutre), `setModulationSettings` (validé contre `current()` : `0 ≤ min < max ≤ 100`, largeur ≥ `minBandWidthPts`, puissance dans `[powerMin, powerMax]`, `|biais| ≤ biasMax` ; ne touche jamais `riskCursor`, qui vaut `DEFAULT_RISK_CURSOR` à la création de ligne), `effectiveSettings` (valeurs stockées **clampées** aux bornes admin courantes ; bande trop étroite élargie autour de son centre, décalée pour rester dans [0, 100] ; consommé à l'étape 2).
- **API** : voir [`../api/rest-endpoints.md`](../api/rest-endpoints.md) (`/api/admin/rainbow-modulation`, `/api/user/modulation-settings`).

### Moteur de modulation (`LiveSizing`, par lien)
- **Calcul pur** `service/modulation/ExposureModulator` : marges de régulation `m % × (max − min)` à l'intérieur de chaque borne, `s` linéaire clampé puis `l = s²(3 − 2s)` ; achat × `(1 − l_haute)(1 + (G − 1)·l_basse)`, vente × `(1 + (G − 1)·l_haute)(1 − l_basse)` (`G = sellBoostMax`). Marge haute seulement si `max < 100`, basse seulement si `min > 0` : la bande neutre [0, 100] ne module rien. Plafond dur en USD : achat ≤ `max·V − P`, vente ≤ `P − min·V` (plancher 0).
- **Chaîne** (`LiveModulation`) : quantité du signal × `puissance·(1 ± biais)` × facteur de bande ; le produit par côté est plafonné à `modulationProductMax` ; puis plafond dur, puis les plafonds existants (cash du `CashLedger`, position tradable). Montant final = ce que lit le plan d'ordres. `effetRisque` (macro) = 1, pas encore branché.
- **Exposition** (`ExposureLedger`/`ExposureBook`, un par wallet et par passe) : `P` = Σ quantité × clôture D1 de la passe (demandes des presets, aucun appel exchange en plus), `V = P + cash USDC` constant ; achat accepté ⇒ `P +=`, vente ⇒ `P −=` pour le lien suivant ; rejeu du même jour : l'action d'origine met le ledger à jour. Prix manquant pour un actif détenu ou `V = 0` ⇒ exposition **inconnue** : pas de modulation de bande (puissance et biais restent appliqués), `exposureStatus = UNKNOWN` au journal.
- **`BAND_LIMIT`** (`LiveBlockReason`) : le signal voulait une action mais la modulation l'a ramenée à 0 ⇒ `NONE` + `BAND_LIMIT`.
- **Journal** : `RainbowLiveLiveBlock.modulation` (JSON, colonne `live_modulation`) : montants du signal, puissance, biais, facteurs de côté, bande, exposition avant/après, `l` haute/basse, facteurs de bande et produit, plafonds atteints, paramètres admin utilisés, montant final. Exposé en `modulation` dans le snapshot de `GET /api/rainbow-live/live-wallet`. Hors de `OrderPlanner.inputsHash` (qui ne lit que statut, action, montant, quantité, carry, cash) : le rejeu du même jour reste `unchanged`.
- Réglages neutres (aucune ligne ou colonnes nulles) ⇒ montants identiques à ceux d'avant la modulation (test de non-régression).

### Montant de base du lien

`RainbowLiveBinding.baseAmount` (`Double` nullable, choisi par l'utilisateur ; nul ⇒ montant du preset, qui suit la stratégie et n'est pas modifiable). `LiveDemand` porte le montant de base avec lequel le signal a été dimensionné ; `withLinkBaseAmount` met l'**achat** à l'échelle `baseAmount lien / baseAmount preset` (la vente, fraction de la position, n'en dépend pas) avant `LiveSizing`. Validation : > 0 et fini (`RainbowLiveBindingService`, `resetBaseAmount` remet à nul). Tests : `LiveDemandTest`, `RainbowLiveBindingControllerTest#linkBaseAmount`.

### Onboarding (`RainbowLiveOnboardingService`, `/api/rainbow-live/onboarding`)

- **Liaison** (`POST /link`) : par actif de `RainbowLiveDefaultPresets.ASSETS`, lien existant ⇒ inchangé ; sinon `BindingCheck` ; `OK` / `TRADABLE_VIA_INTERMEDIARY` ⇒ lien **inactif** sur le premier preset système de l'actif (`bagPercent`/`priority` par défaut) ; tout autre statut (non tradable sans fiat, clé rejetée, soldes illisibles…) ⇒ non lié, statut et raison retournés (rejouable).
- **Proposition** (`GET /proposals?days=`) : `baseAmount = cash du wallet / nb de liens du wallet / (jours × multiplicateur moyen)` ; `jours` = durée choisie par l'utilisateur (champ « Étaler le cash sur », jours ou mois de 30 j), sinon `autonomyDays` admin, borné par les limites absolues de ce paramètre ; multiplicateur moyen = moyenne de `multX2`, `multX1`, `multX0_5` du jeu du preset (jeu Bear pour un Trend Mix), arrondi par défaut au centime. Cash lu par `RealPortfolioSource` (illisible ou nul ⇒ pas de proposition). Le montant est coté via `BindingPathQuoteService` : `BELOW_MIN`, niveau Fee Test et avertissements remontés ; devis indisponible ⇒ proposition gardée avec avertissement. Bande proposée : neutre (`ModulationDefaults`), aucun profil utilisateur n'existe.
- **UI** : carte « Démarrage » (`#rl-onb-panel`, `rainbow-live.js`) au-dessus du bloc Modulation : explication repliable, choix du wallet, « Lier mes actifs », « Montants proposés » (deux colonnes d'autonomie : « proposée » = durée choisie, « actuelle » = cash alloué / (montant en place × multiplicateur moyen), qui ne dépend pas de la durée choisie), « Appliquer » ⇒ `PUT /bindings/{id}`. Le déclenchement est manuel : la sauvegarde d'une clé TRADE ne lie rien toute seule.
- Tests : `RainbowLiveOnboardingServiceTest`.
