# Rainbow live — Dimensionnement réel, chemin d'achat, groupes d'actifs

Suite de [`08-rainbow-live.md`](08-rainbow-live.md) (Rainbow DCA ATR live — Affectations, signal quotidien, liens (bindings), API REST).

## Dimensionnement sur le portefeuille réel (par lien)

Une Affectation liée par au moins un binding est dimensionnée, **une fois par lien**, sur le portefeuille réel en LECTURE SEULE (aucun ordre). Une Affectation sans lien produit son signal (run) mais aucun run de lien.
- **Port** `RainbowPortfolioSource` : `liveSlots(user)` (`LiveSlot(bindingId, affectationId, assetSymbol, walletId, priority, bagPercent, candleSource)` triés par `priority`). Implémentation `RealPortfolioSource` (seul bean du bench à toucher l'exchange) : `read(binding)` → `PortfolioReading(cash USD, cashByMember, positions, fetchedAt, status OK|UNAVAILABLE|NOT_TRADABLE, walletId)` ; `BindingCheck` à chaque passe, puis soldes disponibles via `ReadOnlyBalanceReader`, cache 60 s. Périmètre BTC/ETH/PAXG + membres du groupe `USD` (cash = USDC, détail par membre conservé ; le stock en transit actif est déduit de la position du lien portant la même devise), autres soldes ignorés. Panne, clé rejetée, binding KO, lecture sans aucun solde du périmètre ⇒ `UNAVAILABLE` (jamais un 0 silencieux). `NOT_TRADABLE_WITHOUT_FIAT` ⇒ `NOT_TRADABLE` (soldes non lus, aucune action). Chaque `BindingCheck` persiste `tradability`, `quoteMember`, `routeKey`, `tradabilityCheckedAt` sur le binding ; `ExecutionGuard.requireExecutable(binding)` est le point de passage obligatoire de l'exécution (refus si le statut persisté n'est pas `OK`).
- **Ordre et cash commun** (`CashLedger`) : par utilisateur, liens d'abord par `priority` croissante (puis rang d'actif, puis `bindingId`), un ledger par wallet (pool USD = USDC créé à la première lecture OK). Achat accepté ⇒ cash réservé ; achat > cash restant ⇒ **tout-ou-rien**, action `BLOCKED` + `INSUFFICIENT_CASH`. Les ventes ne sont pas créditées le jour même.
- **Position tradable** = `bagPercent`/100 × position réelle (dynamique) ; vente plafonnée à la position tradable (`LiveSizing`). Achat et vente le même jour : la vente l'emporte.
- **Snapshot par lien** (`RainbowLiveBindingRun`) : voir `RainbowLiveLiveBlock`. Une panne d'un lien n'affecte pas les autres. `UNAVAILABLE` ⇒ `NONE` + raison `UNAVAILABLE`, WARN.
- **Recalcul forcé du jour** : `RainbowLiveExecutionService#recomputeDay(user, asOf, day)` supprime les runs d'Affectation et de lien de l'utilisateur pour le jour puis rejoue sa passe sur la bougie courante (action figée et réservation de cash levées ; le `CashLedger` n'est pas persisté). Déclenché par le reset d'un plan du jour UTC ouvert ([`10-execution-plan.md`](10-execution-plan.md)), jamais si un ordre est parti.
- **Rejeu du même jour** : snapshot et action live d'origine conservés ; un achat d'origine reste réservé dans le pool (pas de nouvelle lecture exchange). Le lendemain, une nouvelle lecture est faite pour le nouveau jour ; le snapshot de la veille n'est pas modifié.
- **Garde** `RainbowLiveNoExchangeDependencyTest` : seules les implémentations de `RainbowPortfolioSource` peuvent dépendre de `service.connector`/`Wallet`/`ProviderApiService` dans le package du bench ; le port n'a aucune méthode d'ordre.

## Chemin d'achat chiffré : frais, carnet, PathFinder, Fee Test (lecture seule, aucun ordre)

Calcul **à la demande** (`GET /api/rainbow-live/bindings/{id}/path-quote?amount=`, cf. [`../api/rest-endpoints.md`](../api/rest-endpoints.md)) ; aucun job, aucune écriture hors cache du catalogue. `BindingPathQuoteService` (`service/dca/atr/binding`) : binding du user (sinon 404) → soldes du wallet (`ReadOnlyBalanceReader`) filtrés sur les membres du groupe `USD` (sources) → catalogue → `PathFinder` avec un marché réel (`LegMarketSource`).
- **Frais réels** : `TradingFeeProvider` / `OkxTradingFeeProvider` (`GET /api/v5/account/trade-fee?instType=SPOT&instId=…`, clé Read du wallet, signature HMAC partagée avec `OkxBalanceReader` dans `OkxSignedRequests`). Taux OKX signés (négatif = frais payé) normalisés en `FeeRate(makerPct, takerPct)` en % (positif = coût) ; champs `maker/taker` pour les paires USDT, `makerUSDC/takerUSDC` pour les paires USDC ; champ absent ⇒ `BalanceUnavailableException` (jamais de frais supposé). Cache mémoire 24 h sur `DomainClock` (échecs non cachés), throttle 500 ms entre appels réseau. Compte OKX de Clem (EEA, niveau « Utilisateur régulier ») : 0,10 % maker / 0,20 % taker, 0 % sur `USDC-USDT`. Le coût d'une jambe utilise le taux **taker** (ordres limit IOC prévus). Clé rejetée (50100-50114) ⇒ `CredentialRejectedException`.
- **Frais réels Kraken** : `KrakenTradingFeeProvider` (`POST /0/private/TradeVolume` `pair=<nativePair>&fee-info=true`, clé Read, signature `KrakenSignedRequests`). `fees` = taker, `fees_maker` = maker, déjà en % ; champ absent ⇒ `BalanceUnavailableException`. Cache 24 h par (clé, instrument), échecs non cachés, throttle 1 s.
- **Carnet public** : `OrderBookClient` / `OkxOrderBookClient` (`GET /api/v5/market/books?instId=&sz=50` → `OrderBookSnapshot`) ; repli `GET /api/v5/market/ticker` (un niveau par côté) marqué `estimation=TICKER` (slippage non chiffré). Un appel par devis, pas de cache. Kraken : `KrakenOrderBookClient` (`GET /0/public/Depth?pair=<nativePair>&count=`, repli `/0/public/Ticker` marqué `TICKER`), paire lue au catalogue (`nativePair`, repli `KrakenAssetNames.fallbackPair`) ; le catalogue expose des `inst_id` en symboles standard (`KrakenAssetNames`).
- **`PathFinder`** (`service/market/instrument`, pur) : arêtes BUY `QUOTE→BASE` (ask) et SELL `BASE→QUOTE` (bid) pour chaque paire du catalogue ; paires touchant un nœud interdit ignorées (fiat : `ExecutionDefaults.FIAT_CURRENCIES` ; `USDT` ; surcharge `tradeio.execution.forbidden-nodes`, liste CSV) ; sources = devises détenues ; profondeur ≤ `MAX_PATH_DEPTH` (2), énumération exhaustive. Intermédiaires autorisés `ExecutionDefaults.INTERMEDIARIES` (BTC, ETH), choisis automatiquement `CHOSEN_INTERMEDIARIES` (BTC seul) : une route ETH est chiffrée et exposée (`chosen=false`), jamais retenue. Coût d'une jambe = frais taker + demi-spread + slippage au montant (VWAP du carnet, `BookSlippage`) ; route = **somme brute**. Jambes dimensionnées en séquence sur le **net reçu** de la précédente ; `sz` ⌊⌋ au `lotSz` en BUY, ⌈⌉ en SELL, `minSz`/`costMin` ⇒ `BELOW_MIN`. Résultat `PathQuote(status OK|NO_PATH|BELOW_MIN, source, legs[], totalCostPct, feeTestLevel, estimation BOOK|TICKER, underfunded, routeKey, routes[RouteQuote])` ; `NO_PATH` ⇒ « non tradable sans monnaie fiat ». Vente : route vers USDC (`X>USDC` ou `X>BTC>USDC`).
- **`FeeTest`** (pur) : coût total < `warn-pct` ⇒ GREEN ; de `warn` à `red` **inclus** ⇒ WARNING ; > `red` ⇒ RED. Seuils lus à chaque appel dans `ExecutionControl.feeWarnPct` / `feeRedPct` via `ExecutionControlService` (défauts 0,2 / 0,8 posés par `ExecutionControlInitializer`, qui lit d'abord les propriétés `tradeio.execution.fee-test.warn-pct` / `red-pct` si la base est vide ; éditables dans l'onglet admin « Plafonds »). `new FeeTest()` / `new FeeTest(warn, red)` = seuils fixes (tests). Pourcentages exposés en %, jamais en bps.
- Gardes : `ConnectorNoOrderMethodTest` et `RainbowLiveNoExchangeDependencyTest` ; aucune méthode d'ordre dans ces chemins.

## Groupes d'actifs (USD = USDC)

- Tables `asset_group` (`code` unique, `valuation` = `NOMINAL`) et `asset_group_member` (`asset_id` **unique** : un actif dans un seul groupe, `position` = ordre de préférence, 0 = membre de cotation privilégié). `AssetGroupInitializer` (`@Order(2)`, après `AssetInitializer`) sème `USD` = USDC (0), idempotent (USDT exclu partout, `ExecutionDefaults.EXCLUDED_STABLE`), jamais écrasé. Code `USD` défini une seule fois : `AssetGroup.USD`.
- `AssetGroupService` : `groupBySymbol()`, `members(code)`, `byMember(code, soldes)`. Valorisation **nominale** (1 membre = 1 unité du groupe, écart de peg ignoré, aucun appel de prix).
- Home (`AssetOverviewService`) : les membres d'un groupe (et leurs `LD*` Binance) sont agrégés en une ligne au code du groupe (« USD »), prix 1. Le fiat `USD` (ZUSD Kraken) est ignoré pour ne pas fusionner avec le groupe.
- Wallet réel : le cash est `Σ` des soldes des membres (`cashUsd`, détail `cashByMember` persisté en JSON dans `cash_detail` du bloc live). USDT est ignoré (hors périmètre).
