# Rainbow live — Dimensionnement réel, chemin d'achat, groupes d'actifs

Suite de [`08-rainbow-live.md`](08-rainbow-live.md) (Rainbow DCA ATR live — Affectations, signal quotidien, liens (bindings), API REST).

## Dimensionnement sur le portefeuille réel (par lien)

Une Affectation liée par au moins un binding est dimensionnée, **une fois par lien**, sur le portefeuille réel en LECTURE SEULE (aucun ordre). Une Affectation sans lien produit son signal (run) mais aucun run de lien.
- **Port** `RainbowPortfolioSource` : `liveSlots(user)` (`LiveSlot(bindingId, affectationId, assetSymbol, walletId, priority, bagPercent, candleSource)` triés par `LiveSlot.SERVICE_ORDER`). Implémentation `RealPortfolioSource` (seul bean du bench à toucher l'exchange) : `read(binding)` → `PortfolioReading(cash USD, cashByMember, positions, fetchedAt, status OK|UNAVAILABLE|NOT_TRADABLE, walletId)` ; `BindingCheck` à chaque passe, puis soldes disponibles via `ReadOnlyBalanceReader`, cache 60 s. Périmètre : actifs liés de l'utilisateur (`AssetRegistry.linkedAssets(user)`) + membres du groupe `USD` (cash = USDC, détail par membre conservé ; le stock en transit actif est déduit de la position du lien portant la même devise), autres soldes ignorés. Panne, clé rejetée, binding KO, lecture sans aucun solde du périmètre ⇒ `UNAVAILABLE` (jamais un 0 silencieux). `NOT_TRADABLE_WITHOUT_FIAT` ⇒ `NOT_TRADABLE` (soldes non lus, aucune action). Chaque `BindingCheck` persiste `tradability`, `quoteMember`, `routeKey`, `tradabilityCheckedAt` sur le binding ; `ExecutionGuard.requireExecutable(binding)` est le point de passage obligatoire de l'exécution (refus si le statut persisté n'est pas `OK`).
- **Ordre et cash commun** (`CashLedger`) : par utilisateur, liens d'abord par `priority` croissante, puis **ancienneté du lien** (`bindingId` croissant ; plus de rang BTC / ETH / PAXG), un ledger par wallet (pool USD = USDC créé à la première lecture OK). Achat accepté ⇒ cash réservé ; achat > cash restant ⇒ **tout-ou-rien**, action `BLOCKED` + `INSUFFICIENT_CASH`. Les ventes ne sont pas créditées le jour même.
- **Position tradable** = `bagPercent`/100 × position réelle (dynamique) ; vente plafonnée à la position tradable (`LiveSizing`). Achat et vente le même jour : la vente l'emporte.
- **Snapshot par lien** (`RainbowLiveBindingRun`) : voir `RainbowLiveLiveBlock`. Une panne d'un lien n'affecte pas les autres. `UNAVAILABLE` ⇒ `NONE` + raison `UNAVAILABLE`, WARN.
- **Recalcul forcé du jour** : `RainbowLiveExecutionService#recomputeDay(user, asOf, day)` supprime les runs d'Affectation et de lien de l'utilisateur pour le jour puis rejoue sa passe sur la bougie courante (action figée et réservation de cash levées ; le `CashLedger` n'est pas persisté). Déclenché par le reset d'un plan du jour UTC ouvert ([`10-execution-plan.md`](10-execution-plan.md)), jamais si un ordre est parti.
- **Rejeu du même jour** : snapshot et action live d'origine conservés ; un achat d'origine reste réservé dans le pool (pas de nouvelle lecture exchange). Le lendemain, une nouvelle lecture est faite pour le nouveau jour ; le snapshot de la veille n'est pas modifié.
- **Garde** `RainbowLiveNoExchangeDependencyTest` : seules les implémentations de `RainbowPortfolioSource` peuvent dépendre de `service.connector`/`Wallet`/`ProviderApiService` dans le package du bench ; le port n'a aucune méthode d'ordre.

## Chemin d'achat chiffré : frais, carnet, PathFinder, Fee Test (lecture seule, aucun ordre)

Calcul **à la demande** (`GET /api/rainbow-live/bindings/{id}/path-quote?amount=`, cf. [`../api/rest-endpoints.md`](../api/rest-endpoints.md)) ; aucun job, aucune écriture hors cache du catalogue. `BindingPathQuoteService` (`service/dca/atr/binding`) : binding du user (sinon 404) → soldes du wallet (`ReadOnlyBalanceReader`) filtrés sur les membres du groupe `USD` (sources) → catalogue → `PathFinder` avec un marché réel (`LegMarketSource`).
- **Service de frais unique** `TradingFeeService` (`service/connector/fee`) : seul point d'accès aux frais pour le plan d'ordres, le devis de chemin (`BindingPathQuoteService`, onboarding / ajout d'un lien), le re-devis d'exécution (`StepRequoter`) et le simulateur (`ReplayScheduleBuilder`). Cache 24 h (`ExecutionDefaults.FEE_CACHE_TTL`, horloge `DomainClock`) en mémoire puis **persisté** (`trading_fee_cache`, migration `V3`, FK `ON DELETE CASCADE` sur le credential, aucune clé ni secret) : survit au redémarrage. Clé = (credential, instrument) ; palier valable pour tout le compte (`TradingFeeProvider#accountWide()` : Revolut X, Bitvavo, One Trading) = (credential, `*`). Échecs non cachés, single-flight par clé. Deux vues : **stricte** (`forProvider`, plan d'ordres et re-devis : valeur périmée + échec ⇒ exception) et **estimation** (`lenient`, devis / onboarding / simulateur : valeur périmée acceptée si l'exchange est injoignable, avertissement « Frais du compte de plus de 24 h »). `warm(...)` préchauffe les entrées manquantes avant le rejeu. Les `TradingFeeProvider` ne font que la récupération réseau (throttle compris), sans cache.
- **Frais réels OKX** : `TradingFeeProvider` / `OkxTradingFeeProvider` (`GET /api/v5/account/trade-fee?instType=SPOT&instId=…`, clé Read du wallet, signature HMAC partagée avec `OkxBalanceReader` dans `OkxSignedRequests`). Taux OKX signés (négatif = frais payé) normalisés en `FeeRate(makerPct, takerPct)` en % (positif = coût) ; champs `maker/taker` pour les paires USDT, `makerUSDC/takerUSDC` pour les paires USDC ; champ absent ⇒ `BalanceUnavailableException` (jamais de frais supposé). Compte OKX de Clem (EEA, niveau « Utilisateur régulier ») : 0,10 % maker / 0,20 % taker, 0 % sur `USDC-USDT`. Le coût d'une jambe utilise le taux **taker** (ordres limit IOC prévus). Clé rejetée (50100-50114) ⇒ `CredentialRejectedException`.
- **Frais réels Kraken** : `KrakenTradingFeeProvider` (`POST /0/private/TradeVolume` `pair=<nativePair>&fee-info=true`, clé Read, signature `KrakenSignedRequests`). `fees` = taker, `fees_maker` = maker, déjà en % ; champ absent ⇒ `BalanceUnavailableException`. Throttle 1 s (cache : voir `TradingFeeService`).
- **Carnet public** : `OrderBookClient` / `OkxOrderBookClient` (`GET /api/v5/market/books?instId=&sz=50` → `OrderBookSnapshot`) ; repli `GET /api/v5/market/ticker` (un niveau par côté) marqué `estimation=TICKER` (slippage non chiffré). Un appel par devis, pas de cache. Kraken : `KrakenOrderBookClient` (`GET /0/public/Depth?pair=<nativePair>&count=`, repli `/0/public/Ticker` marqué `TICKER`), paire lue au catalogue (`nativePair`, repli `KrakenAssetNames.fallbackPair`) ; le catalogue expose des `inst_id` en symboles standard (`KrakenAssetNames`).
- **`PathFinder`** (`service/market/instrument`, pur) : arêtes BUY `QUOTE→BASE` (ask) et SELL `BASE→QUOTE` (bid) pour chaque paire du catalogue ; paires touchant un nœud interdit ignorées (fiat : `ExecutionDefaults.FIAT_CURRENCIES` ; `USDT` ; surcharge `tradeio.execution.forbidden-nodes`, liste CSV) ; sources = devises détenues ; profondeur ≤ `MAX_PATH_DEPTH` (2), énumération exhaustive. Intermédiaires autorisés `ExecutionDefaults.INTERMEDIARIES` (BTC, ETH), choisis automatiquement `CHOSEN_INTERMEDIARIES` (BTC seul) : une route ETH est chiffrée et exposée (`chosen=false`), jamais retenue. Coût d'une jambe = frais taker + demi-spread + slippage au montant (VWAP du carnet, `BookSlippage`) ; route = **somme brute**. Jambes dimensionnées en séquence sur le **net reçu** de la précédente ; `sz` ⌊⌋ au `lotSz` en BUY, ⌈⌉ en SELL, `minSz`/`costMin` ⇒ `BELOW_MIN`. Résultat `PathQuote(status OK|NO_PATH|BELOW_MIN, source, legs[], totalCostPct, feeTestLevel, estimation BOOK|TICKER, underfunded, routeKey, routes[RouteQuote])` ; `NO_PATH` ⇒ « non tradable sans monnaie fiat ». Vente : route vers USDC (`X>USDC` ou `X>BTC>USDC`).
- **`FeeTest`** (pur) : coût total < `warn-pct` ⇒ GREEN ; de `warn` à `red` **inclus** ⇒ WARNING ; > `red` ⇒ RED. Seuils lus à chaque appel dans `ExecutionControl.feeWarnPct` / `feeRedPct` via `ExecutionControlService` (défauts 0,2 / 0,8 posés par `ExecutionControlInitializer`, qui lit d'abord les propriétés `tradeio.execution.fee-test.warn-pct` / `red-pct` si la base est vide ; éditables dans l'onglet admin « Plafonds »). `new FeeTest()` / `new FeeTest(warn, red)` = seuils fixes (tests). Pourcentages exposés en %, jamais en bps.
- Gardes : `ConnectorNoOrderMethodTest` et `RainbowLiveNoExchangeDependencyTest` ; aucune méthode d'ordre dans ces chemins.

## Groupes d'actifs (USD = USDC)

- Tables `asset_group` (`code` unique, `valuation` = `NOMINAL`) et `asset_group_member` (`asset_id` **unique** : un actif dans un seul groupe, `position` = ordre de préférence, 0 = membre de cotation privilégié). `AssetGroupInitializer` (`@Order(2)`, après `AssetInitializer`) sème `USD` = USDC (0), idempotent (USDT exclu partout, `ExecutionDefaults.EXCLUDED_STABLE`), jamais écrasé. Code `USD` défini une seule fois : `AssetGroup.USD`.
- `AssetGroupService` : `groupBySymbol()`, `members(code)`, `byMember(code, soldes)`. Valorisation **nominale** (1 membre = 1 unité du groupe, écart de peg ignoré, aucun appel de prix).
- Home (`AssetOverviewService`) : les membres d'un groupe (et leurs `LD*` Binance) sont agrégés en une ligne au code du groupe (« USD »), prix 1. Le fiat `USD` (ZUSD Kraken) est ignoré pour ne pas fusionner avec le groupe.
- Wallet réel : le cash est `Σ` des soldes des membres (`cashUsd`, détail `cashByMember` persisté en JSON dans `cash_detail` du bloc live). USDT est ignoré (hors périmètre).

## Volume 24 h au catalogue et éligibilité d'un actif (socle des actifs dynamiques)

Décisions : [`../decisions/actifs-dynamiques.md`](../decisions/actifs-dynamiques.md). L'éligibilité est appelée à la création d'un lien (voir « Registre d'actifs et liens dynamiques ») et par l'endpoint des actifs éligibles.

- **Volume 24 h** : lu par le client de liste **dans le rafraîchissement du catalogue** (un appel « toutes les paires » par exchange et par refresh, jamais par paire) et stocké en **monnaie de cotation** (`exchange_instrument.volume_24h_quote`, date `volume_read_at`). Sources : OKX `GET /api/v5/market/tickers?instType=SPOT` (`volCcy24h`) ; Kraken `GET /0/public/Ticker` sans paire (`v[1]` × VWAP `p[1]`) ; Gate EU `GET /spot/tickers` (`quote_volume`) ; Bitvavo `GET /ticker/24h` (`volumeQuote`) ; One Trading `GET /market-ticker` (`quote_volume`) ; **Revolut X : aucun volume public** (nul). L'échec de l'appel de volume n'empêche pas le catalogue (WARN, volume inconnu) ; un volume nul ne remplace jamais une valeur déjà lue. Les formats Gate EU, Bitvavo, One Trading et Kraken Ticker sont lus d'après la documentation des exchanges, pas vérifiés en réel (réseau sortant indisponible au moment du développement) : à contrôler au premier refresh en dev.
- **`AssetEligibilityService.check(actif, provider)`** (`service/market/eligibility`) renvoie `Result(éligible, raison, volumeUsd, volumeVerified, d1Days)`. Première règle violée, dans l'ordre (le réseau en dernier) :
  1. **Noms** (`AssetNameRules`, pur) : `FIAT` (`ExecutionDefaults.FIAT_CURRENCIES`), `STABLECOIN` (liste `STABLECOINS`), `LEVERAGED_TOKEN` (`BTC3L`, `ETH5S`, `…UP/DOWN/BULL/BEAR`, racine ≥ 2 car.), `EARN_OR_WRAPPED` (liste `WRAPPED` pour tous les providers + encodage propre au provider : **Kraken** tout suffixe `.X` (`.S .F .M .B .P .T`) et `ETH2` ; **Binance** préfixe `LD` suivi d'au moins 3 car., `LDO` reste valide). Le client Kraken écarte déjà les bases suffixées avant le catalogue ; la règle est une seconde ligne de défense.
  2. `BLOCKLISTED` : table `asset_blocklist` (symbole unique, motif, auteur, date). Administration (ajout, retrait, liste, seuil de volume) : onglet « Actifs » de `/admin` ([`11-front-app.md`](11-front-app.md), endpoints : [`../api/rest-rainbow-live.md`](../api/rest-rainbow-live.md)), service `AdminAssetsService`. Aucun cache : `LinkStateService` et `AssetEligibilityService` relisent la table à chaque appel ⇒ ajout / retrait effectifs sans redémarrage (liens existants suspendus + alarme, nouveaux liens refusés). Symbole normalisé par `AssetEligibilityDefaults.normalizeSymbol` (`[A-Z0-9]{2,16}`, source unique, reprise par la création de lien) ; doublon ou invalide ⇒ 400. **Journal d'audit sans changement de schéma** : `AdminAction` est une colonne enum en base, donc les écritures réutilisent `AdminAction.MODULATION` avec cible préfixée (`asset-blocklist:<SYM>`, `asset-settings:min-volume`, `new-asset-recompute:<ACTIF>`) et payload JSON ; une valeur dédiée exigerait une migration.
  3. `CATALOG_UNAVAILABLE` (catalogue absent et exchange injoignable : ni éligible ni refus définitif) puis `NO_BUY_ROUTE` : `PathFinder.routes` depuis `USDC` sur le catalogue en base, ≤ 2 jambes, mêmes nœuds interdits que le chemin d'achat (fiat, USDT), passerelle BTC comprise (PAXG sur Kraken éligible via `USDC>BTC>PAXG`), jamais via un intermédiaire « affichage seul » (ETH).
  4. `VOLUME_TOO_LOW` : somme des volumes des paires **live** de l'actif cotées USD / USDC / USDT chez ce provider (pas de conversion de change : une cotation EUR ou BTC n'est pas additionnée) < réglage admin `asset_eligibility_settings.min_volume_usd` (ligne unique créée par `AssetEligibilitySettingsInitializer`, défaut `AssetEligibilityDefaults.DEFAULT_MIN_VOLUME_USD` = 1 000 000 USD ; édition : `AssetEligibilitySettingsService.updateMinVolumeUsd`). **Volume inconnu** (exchange sans volume, lecture de plus de 7 jours, aucune paire cotée en USD) : **éligible mais non vérifié** (`volumeVerified = false`, constante `UNKNOWN_VOLUME_ELIGIBLE` ; `false` ⇒ refus `VOLUME_UNKNOWN`). Choix d'implémentation, à confirmer par Clem ; l'onglet « Actifs » l'affiche en « volume non vérifiable ».
  5. `HISTORY_TOO_SHORT` / `HISTORY_UNAVAILABLE` : au moins `AssetEligibilityDefaults.MIN_D1_DAYS` (120, source unique, reprise par `NewAssetConfig.minCandles`) jours de bougies D1 closes chez le provider (`CachedD1HistoryProbe` → `MarketDatasetEngine.getDailyDatasetOnSource`, borne = la veille 00:00 UTC : une fois les 120 bougies en base, plus aucun appel réseau ; ni `asset_provider` ni écriture de configuration). Provider sans client de bougies (Bitvavo, Gate EU, One Trading) : 0 jour. Lecture impossible (réseau) : `HISTORY_UNAVAILABLE`, à réessayer.
- **`ExecutionDefaults.displayOnlyIntermediaries()`** : source unique des intermédiaires « affichage seul » (partagée par `PathFinder` via `BindingPathQuoteService`, `OrderPlanner` et l'éligibilité).
- Tests : `AssetNameRulesTest`, `AssetEligibilityServiceTest`, `CachedD1HistoryProbeTest`, `AssetEligibilityPersistenceTest`, `InstrumentVolumeParsingTest`, `InstrumentCatalogTest`, `ActifsDynamiquesMigrationTest` (V10), `AdminAssetsServiceTest` (liste noire ajout / retrait / doublon / invalide, effet immédiat sans redémarrage, seuil, vue par actif dont volume non vérifiable, journal), `AdminAssetsControllerSecurityTest` (anonyme et non-admin refusés).

## Registre d'actifs et liens dynamiques (moteur)

Plus de liste figée : `AssetRegistry` (`service/dca/atr/bench`) est la source unique. Un actif « existe » pour un utilisateur quand il porte un lien non archivé (`linkedAssets(user)`, tous utilisateurs : `linkedAssets()`). `AssetRegistry.SEED_ASSETS` (BTC, ETH, PAXG) n'est **pas** un périmètre : c'est le jeu semé au démarrage (presets de base, Affectations Système) et le périmètre par défaut de la liaison automatique d'un wallet (`RainbowLiveOnboardingService.link`) tant que l'écran de choix d'actifs n'existe pas. Listes utilisateur / Expert = actifs liés. `RainbowLiveDefaultPresets.configFor(actif)` retombe sur la config BTC pour un actif sans preset dédié.

- **Création de lien** (`RainbowLiveBindingService.create`) : symbole `[A-Z0-9]{2,16}` ; wallet sans provider ⇒ 400 ; `AssetEligibilityService.require(actif, provider du lien)` ⇒ 400 avec la raison lisible (`IneligibilityReason.label()`, ex. « Actif non éligible : DOGE chez OKX (volume 24 h inférieur au minimum) ») ; puis `AssetLinkBootstrap.prepare` (idempotent, ne modifie jamais l'existant) : ligne `asset` (nom = symbole, `decimals` dérivés du pas de quantité `lotSz` de la paire USDC / USDT / USD du catalogue, à défaut 8), ligne `asset_provider` du provider du lien **seulement si l'actif n'en a aucune** (les lignes existantes ne sont jamais touchées ; les autres providers sont créés à la volée par le moteur de bougies), presets de base copiés du BTC pour tout actif hors `SEED_ASSETS` ; l'Affectation Système « <ACTIF> Système » vient ensuite (`AssetAffectationService.forAsset`). Binance n'est qu'une source de bougies (sans catalogue) : un wallet Binance ⇒ `CATALOG_UNAVAILABLE`. Priorité par défaut = fin de file (max + 1).
- **Rang du cash** : priorité du lien, puis ancienneté (`bindingId`), partout (`LiveSlot`, `CashLedger`, `RainbowLiveExecutionService`, simulation `FullReplayService`, `OrderPlanner`). Pour les liens existants l'ordre à priorité égale passe de BTC / ETH / PAXG à l'ancienneté : seuls les ex æquo de priorité changent.
- **Paire de bougies D1** (`CandlePairResolver`, catalogue en base, aucun réseau) : USDC si la paire existe chez le provider, sinon USDT, sinon USD ; exchange sans catalogue ou actif absent du catalogue ⇒ convention `<ACTIF>USDT` (`ProviderSymbolMapper`). Détail : [`04-market-data.md`](04-market-data.md).
- **État d'un lien** (`LinkStateService`, aucune colonne, recalculé à chaque lecture, catalogue en base) :
  - **suspendu** (`SuspensionReason`) : `BLOCKLISTED` (actif en liste noire), `PROVIDER_DISCONNECTED` (provider ou clé de lecture désactivés / supprimés), `ROUTE_REMOVED` (catalogue chargé du provider sans route d'achat depuis USDC ; un catalogue jamais chargé ne suspend rien). Effet : aucun ordre réel, lien / signaux / simulation visibles, jamais de bascule de provider ;
  - **en attente de validation** : aucune ligne `asset_base_rate` valide (`AssetBaseRateService.isCalibrated`). Effet : simulation seule ; `PUT /bindings/{id}/execution` en `ACTIVE` ⇒ 400 « Actif en attente de validation : simulation seule… ».
  - Défense en profondeur : `OrderPlanService` calcule `holdReason` des liens exécutables et `OrderPlanner` produit un plan `DISABLED` avec la raison en avertissement ; `OrderExecutor` bloque l'actif (`ExecutionBlockReason.LINK_SUSPENDED` / `PENDING_VALIDATION`) avant tout ordre.
- **Alarme Docteur** `LINK_SUSPENDED` : voir [`12-doctor.md`](12-doctor.md).
- **Actifs éligibles** : `EligibleAssetsQueryService` (catalogue en base, aucun appel réseau) ; endpoint dans [`../api/rest-rainbow-live.md`](../api/rest-rainbow-live.md).
- **D1b** : `NewAssetProposalService` se déclenche pour tout lien dont l'actif n'a **aucune ligne `asset_base_rate` valide** ([`15m-pipeline-nouvel-actif.md`](15m-pipeline-nouvel-actif.md)).
- Tests : `LinkStateServiceTest`, `CandlePairResolverTest`, `RainbowLiveBindingDynamicAssetTest`, `LinkSuspensionCheckTest`, `LiveSlotOrderTest`.

### Limites connues (actifs dynamiques)

- Encodages « earn » / staking propres à chaque provider : Kraken xStocks non détectables par le nom.
- Binance sans `InstrumentListClient` : jamais éligible via le catalogue.
- Formats des endpoints de volume Gate EU / Bitvavo / One Trading / Kraken à vérifier au 1er refresh ; volume inconnu (Revolut X) = éligible non vérifié, à confirmer.
- Plusieurs calculs D1b en file : un à la fois, 10 min max chacun.
- Le catalogue ne porte aucun nom d'actif : la recherche de l'onboarding porte sur le symbole seulement.
