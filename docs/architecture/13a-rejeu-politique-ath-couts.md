# Rejeu : politique de modulation, plafond ATH, coûts, épisodes

Vérifié le : 2026-11-16 (`service/expert/simulation/**`, `service/dca/atr/AthCap*`, `service/expert/simulation/policy/**`). Suite de [`13-espace-expert.md`](13-espace-expert.md) (simulateur complet, parité). Recherche automatique de paramètres sur ce rejeu : [`15-optimiseur.md`](15-optimiseur.md).

## Politique de modulation dans le temps (`service/expert/simulation/policy/`)
`MultiLinkReplayEngine.Input.policy` (nullable ; `null` ⇒ comportement strictement inchangé, constructeurs historiques conservés) : interface pure `ModulationPolicy#settingsFor(DayState, ModulationSettings base)`, appelée une fois par jour (un jeu de réglages pour tous les liens, comme le live). `base` = `settingsByDay.getOrDefault(day, in.settings())`. La sortie est bornée par `UserTradingSettingsService.clamp(settings, limits)` (fonction pure statique, même code que `effectiveSettings` : puissance, biais, bande [0, 100] élargie à la largeur minimale, marge) avant d'être appliquée.
- **`DayState`** (record immuable, rien de postérieur au jour courant) : `day`, `cash`, `assetsValue`, `totalValue` (aux clôtures du jour via `ExposureLedger.of` ; exposition inconnue ⇒ valeurs d'actifs de la veille), `peakValue` (max des `totalValue` de fin de journée passés, initial = capital de départ), `drawdownPct` (≤ 0), `exposurePct` (null si inconnue, règle du live), `regimeByAsset` (UP / DOWN / RANGE des liens actifs du jour), `daysInRegimeByAsset` (jours consécutifs, jour courant inclus ; compteur tenu par le moteur, mis à jour sur les barres actives seulement ; 1 à la bascule). Helpers : `majorityRegime()` (égalité ou aucun ⇒ null), `maxDaysInRegime(regime)`.
- **Politiques manuelles** (`ModulationPolicies.from(PolicySpec{type, params})`, validation par champ `policy.type` / `policy.params.<nom>` ⇒ `ExpertValidationException`, paramètres inconnus refusés) : `CONSTANT` (base) ; `REGIME_BAND` (`bullMin`, `bullMax`, `bearMin`, `bearMax` ; bande du régime majoritaire, sinon base) ; `EXPOSURE_GAP_BIAS` (`gain` ]0 ; 10] : biais = `clamp(gain × (cible − exposition)/100, ±1)`, cible = milieu de la bande de base, exposition inconnue ⇒ base ; la borne admin du biais s'applique ensuite) ; `BEAR_DERISK_RAMP` (`bearTarget` [0 ; 100], `rampDays` entier [1 ; 365] : en Bear majoritaire, `exposureMax` décroît linéairement vers `bearTarget`, progression = `min(1, joursEnBear/rampDays)`, jours du lien Bear le plus ancien). Sans ordre de rééquilibrage (décision de Clem), « Bear ⇒ exposition basse » ne fait que couper les achats et accentuer les ventes déjà demandées par le Rainbow.
- **Résultat** : `MultiLinkReplayEngine.Result#policyDays` (`PolicyDay{day, applied, exposurePct, drawdownPct}`, vide sans politique).
- **`FULL`** : `FullRequest.policy` (`PolicySpec`, nullable, additif) ; `FullMetaDto.policy` = libellé de la politique appliquée (null sinon) ; la politique est validée par `FullSimulationService#resolve`. `compute` = `load` (bougies, capital, coûts : `Loaded`) + `run` (un rejeu pour une politique donnée).
- **Comparaison** : `PolicyCompareService` (`POST /api/expert/simulations/full/policy-compare`, mode EXPERT) : un chargement, puis un rejeu `CONSTANT` + N politiques (1 à 5), **synchrone**, un calcul à la fois par utilisateur (409 `SIMULATION_ALREADY_RUNNING`), `withCosts` faux par défaut, aucune écriture. Par run : valeur finale, DCA fixe de même budget, écart (USDC, %), drawdown max, exposition moyenne, répartition du gain (`EpisodeTimeline` : exposition / timing / frais), jours d'ordre refusé (`blockedDays`) et `BELOW_MIN`, durée du rejeu en ms, plafond ATH appliqué (libellé), `maxStakeMultiple` / `maxFinalStakeMultiple` / `cappedBuys` ([plafond de mise ATH](#plafond-de-mise-ath-utilisateur-rejeu)). Chaque variante peut porter son `athCap` (`PolicySpec.athCap`), à défaut celui de `full.athCap` ; la référence `CONSTANT` utilise celui de `full`.

## Plafond de mise ATH utilisateur (rejeu)
Mise d'un achat du signal = `base × facteur ATH × multiplicateur de zone` (jusqu'à 10–15 × la base). `AthCap{buyCap, sellCap}` (`service/dca/atr/`) la plafonne **par-dessus** les paramètres ATH du preset (qui restent le signal) ; `null` / valeurs nulles = aucun plafond = live.
- **Achat** : multiplicateur effectif = `min(facteurATH × multZone, buyCap)` dans `ReferenceSizer(base, athCap)`, sur le **signal**, avant la modulation (puissance, biais, bande ≤ `modulationProductMax`) ; plafond non atteint ⇒ calcul identique à avant.
- **Vente** : facteur effectif = `min(sellAthFac, sellCap)` dans `RainbowAtrStrategy#stepWithMoon` (toujours borné par position, bag protégé, réserve moon). `RainbowSignal` garde les facteurs bruts.
- **Un seul calcul** : `step` / `stepWithMoon`, `ReferenceSizer` et `RainbowAtrReplay#runFull` prennent le plafond en paramètre optionnel (surcharges historiques conservées) ; l'état du moteur (armements, moon, position virtuelle) suit les montants plafonnés. Transport : `LinkSignalReplay.Config.athCap`, posé sur tous les liens par `MultiLinkReplayEngine.Input.athCap` (global à l'utilisateur). `Result#stakeStats` = `{maxStakeMultiple (signal / base, avant modulation), maxFinalStakeMultiple (décidé / base, après modulation), cappedBuys}`.
- **Défauts par profil** (`ModulationDefaults#athCapOf`, constantes de code à valider ; persistance et réglage admin : étape 7) : Prudent 3 / 1, Équilibré 6 / 2, Dynamique 10 / 3, Full 15 / 5 (achat / vente) ; `CUSTOM` : aucun.
- **API** : `FullRequest.athCap {profile, buyCap, sellCap}` (profil = défauts, `buyCap` / `sellCap` explicites surchargent). Validation par champ (`AthCapResolver`, `VALIDATION`) : `athCap.profile`, `athCap.buyCap` ≥ 1, `athCap.sellCap` ≥ 0 (`policies[i].athCap.*` en comparaison). `FullMetaDto.athCap` = libellé appliqué.
- **Live** sans plafond : [`08-rainbow-live.md`](08-rainbow-live.md). Effet mesuré : [`../etudes/etude-optimisation-mode-autonome.md`](../etudes/etude-optimisation-mode-autonome.md) §11.2.

## Coûts dans le rejeu : frais, minimum d'ordre, carry
`MultiLinkReplayEngine.Input.costs` (`Costs(OrderReplay, minBuyUsd par lien, route imposée par lien)`, nul = lots 1-2). Après la décision nominale de `SizingCore` (inchangée), `OrderReplay` (pur) calcule ce qui est **réellement exécuté** avec le même code que le plan d'ordres (`PathFinder#find` + `OrderCore`) sur un marché figé du jour (`FrozenLegMarketSource` : mid = prix USD base / prix USD cotation, bid/ask = mid ∓ demi-spread ; prix du jour = clôtures du rejeu, devise sans historique comme le BTC d'une route PAXG = prix actuel du barème, signalé). Barème (`OrderReplay.Schedule`) construit **avant** la boucle par `ReplayScheduleBuilder` (seule partie réseau) : frais = `TradingFeeService` (estimation, `warm`), spread / slippage = un carnet public actuel par instrument lu une fois, `lotSz` / `minSz` / `costMin` du catalogue. Avertissements : « frais actuels appliqués à toute la période », carnet actuel, frais périmés éventuels.
- **Achat** : mise effective = base du jour + carry ; sous `minBuyUsd` du lien ⇒ `BELOW_MIN`, aucun débit, `carry_out` = mise effective ; plan bloqué (`NO_PATH`, `INSUFFICIENT_FUNDS_AFTER_FEES`, `NOT_TRADABLE_WITHOUT_FIAT`, `BELOW_MIN` exchange) ⇒ aucun débit, carry inchangé (sauf `BELOW_MIN`) ; achat passé ⇒ **cash débité = mise effective** (pas de sur-achat jusqu'au minimum), quantité obtenue = dernière jambe × (1 − frais), `carry_out` = 0. Route imposée du lien (`preferredRoute`) respectée ; jambes en séquence sur le net reçu, 2 jambes le même jour (pas de stock en transit). Carry par lien porté d'un jour au suivant, remis à zéro si le `base_amount` change.
- **Vente** : quantité vendue ⌊⌋ au lot, produit net de frais ; créditée à la fin du jour (jamais le jour même), comme avant.
- **DCA fixe de référence** : mêmes frais / minimum de l'exchange, sans carry. Exposition valorisée aux clôtures ; la position nette de frais alimente le lendemain.
- **Sorties** (`Result.costDays`, `totalCostUsdc`, `fixedTotalCostUsdc`) : par jour et lien : outcome, mise effective, `carry_in` / `carry_out`, route, coût % et USDC, niveau Fee Test, cash et quantité échangés, frais cumulés ; la courbe du wallet est nette de frais.
- **Parité** : `GET /api/expert/simulations/parity?withCosts=true` ajoute `ParityReport.costs` (valeurs finales nettes de frais, frais cumulés, comparaison aux plans d'ordres enregistrés `rainbow_live_order_plan_asset` : outcome, `carry_out`, coût % ; écart de coût classé « frais / carnets d'époque ≠ barème actuel »). Sans plan en base sur la période : note explicite, pas de comparaison. Frais ou carnet indisponibles : note, aucun coût supposé.

### Timeline des épisodes et répartition du gain (lot 4)
`EpisodeTimeline` (fonction pure, `service/expert/simulation/`) calcule, par actif, à partir de `MultiLinkReplayEngine.Result#trades` (`TradeDay` : zone Rainbow du jour, régime — nul = barre inactive —, cours, quantité / cash / coût échangés par la stratégie **et** par le DCA fixe) :
- **Épisodes** : un par suite de jours à même (régime, zone) — changement de zone ou bascule Bull/Bear = nouvel épisode ; barres inactives = épisodes `INACTIF` ; aucune fusion ni durée minimale. Plage `[from, to]` : épisodes tronqués aux bords. Par épisode : actif, régime, zone (`-1` hors bornes, 0 extrême bas, 1 X2, 2 X1, 3 X0,5, 4 pas d'achat, 5 extrême haut), dates, acheté / vendu (USDC, qté), prix de revient moyen de fin, PnL réalisé / latent / total, exposition de début / fin (% du wallet), répartition du gain. Agrégat par (régime, zone).
- **PnL** (prix moyen pondéré, frais inclus, cf. `decisions/definition-pnl.md`) : prix de revient de la position d'ouverture = cours du 1er jour de la plage ; achat = cash réellement payé ; vente au prix de revient moyen courant. PnL d'un épisode = variation de (réalisé cumulé + latent) ; zone neutre ⇒ variation du latent. Invariant : Σ PnL des épisodes de tous les actifs = variation de valeur du wallet sur la plage (ouverture valorisée au cours du 1er jour ; actifs détenus sans lien exclus).
- **Répartition du gain** de l'écart stratégie − DCA fixe, exactement additive par jour donc par épisode : `exposition = d̄·ΔP` ; `timing = (d_{t−1} − d̄)·ΔP + écart d'exécution` (cash + Δq·P + coût, stratégie − référence) ; `frais = −(coût stratégie − coût référence)`. `d = qté stratégie − qté référence`, `d̄` = moyenne de `d_{t−1}` sur la plage. Sur deux sous-plages, les frais s'additionnent ; le partage exposition / timing et le PnL dépendent de l'ouverture et de `d̄` de chaque plage.
- **Accès sans UI** (`ExpertSimulationEpisodesController`, mode EXPERT) : `GET /api/expert/simulations/episodes` rejoue le wallet en continu (mêmes paramètres facultatifs que la parité, `withCosts`), garde les séries en mémoire (`EpisodeResultStore`, TTL et plafond par utilisateur des simulations, rien de persisté) et renvoie `EpisodeReportDto` avec `resultId` ; `GET /api/expert/simulations/episodes/{resultId}?from&to` recalcule sur la sous-plage sans rejeu. Un lien par actif supposé.
