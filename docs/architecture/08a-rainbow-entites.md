# Rainbow live — Entités (schéma)

Suite de [`08-rainbow-live.md`](08-rainbow-live.md) (Rainbow DCA ATR live — Affectations, signal quotidien, liens (bindings), API REST).

## Entités (schéma créé par `ddl-auto=update` ; migration Flyway préparée mais non activée, cf. [`../operations/flyway.md`](../operations/flyway.md))

- `TrendPreset` (`trend_preset`) : réglages du Trend Mix (colonnes typées `TrendMixCalculator.Params`), `rangeMapping` (`KEEP_PREVIOUS|TO_BEAR|TO_BULL` : jeu retenu quand le Trend est RANGE), `assetSymbol` (BTC|ETH|PAXG), `name`, `origin` (`PresetOrigin` SYSTEM|USER), `owner` (nul pour SYSTEM), `baseRole` (`BasePresetRole` : `TREND` pour le preset de base, nul sinon), `revision`, `createdAt`/`updatedAt`. **Unique (asset, base_role)** pour les presets de base et **(owner, asset, name)** pour ceux des utilisateurs.
- `RainbowPreset` (`rainbow_preset`) : `@Embedded RainbowAtrConfig` + `analysisWindowMonths`, mêmes colonnes d'identité (`assetSymbol`, `name`, `origin`, `owner`, `baseRole` ∈ `RAINBOW_BULL|RAINBOW_BEAR|null`, `revision`) et mêmes unicités. **Neutre** : c'est l'Affectation qui l'installe sur UP ou sur DOWN (le même preset peut occuper les deux emplacements).
- `AssetAffectation` (`asset_affectation`) : **une par (user, actif)** (unique), `trendPreset`, `rainbowUp`, `rainbowDown` (FK vers les presets de l'actif, système ou propres à l'utilisateur), `enabled` (activation par l'utilisateur : seule une Affectation active et complète est jouée par la passe, `PATCH /affectations/{id}/enabled`), `createdAt`/`updatedAt`. `isComplete()` = les trois presets présents ; `label()` = « <nom Up> / <nom Down> ». Le Trend choisit chaque jour le preset Rainbow joué : UP ⇒ `rainbowUp`, DOWN ⇒ `rainbowDown`, RANGE selon `rangeMapping`.
- `RainbowAtrConfig` (`@Embeddable`) : 1 colonne typée par paramètre = `RainbowAtrTuning` (17) + `RainbowAtrGlobals` (12 + `multX2/X1/X0_5/Triggered` + `baseAmount`). `of(tuning, globals)`, `toTuning()`, `toGlobals()`, `hash()` (SHA-256 tronqué). `baseAmount` n'existe que dans la config. Réutilisé tel quel (mêmes noms de colonnes) comme snapshot dans le run.
- **Presets système de base** (`ExpertBasePresetService`, `ExpertBasePresetInitializer` `@Order(61)`) : 9 presets, 3 par actif — « Trend de base » (`TREND`), « <actif> Bull » (`RAINBOW_BULL`, jeu de `RainbowLiveDefaultPresets`/`RainbowAtrPresets`) et « <actif> Bear » (`RAINBOW_BEAR`). Créés s'ils sont absents, **jamais modifiés** ; une relance ne duplique rien. `AssetAffectationService#ensureAffectations(user)` (appelé par la passe et par `GET /affectations`) crée, pour chaque actif où l'utilisateur n'en a pas, une Affectation **inactive** sur ces presets de base (Bull ⇒ UP, Bear ⇒ DOWN).
- `RainbowLivePresetEvent` (`rainbow_live_preset_event`) : historique des changements d'Affectation d'un user (`type` ENABLE | DISABLE | LIVE_SWITCH, `assetSymbol`, libellé avant/après sans FK, `occurredAt` via `DomainClock`, `reason`), `ON DELETE CASCADE` sur le user. Écrit par `RainbowLivePresetEventService` : activation/désactivation effective, changement des presets installés, création/bascule d'un binding (`LIVE_SWITCH`).
- `RainbowLiveEngineState` (`rainbow_live_engine_state`) : unique (Affectation, `state_day`), `ON DELETE CASCADE` ; état de la machine Rainbow (`RainbowAtrState` : armements, verrou, cooldown, réserve moon, automate moon) + **`positionQty`** (position VIRTUELLE du moteur, base de la réserve moon et des ventes, indépendante de tout wallet) + `configHash` (empreinte de la config effective : fenêtre + presets Rainbow UP/DOWN + preset Trend) à la FIN du jour. NaN stockés `null`.
- `RainbowAthReference` (`rainbow_ath_reference`) : unique (actif, `ref_day`) ; ATH par ACTIF valable à la fin du jour (une ligne par jour : le run du lendemain relit l'ATH de la veille).
- `RainbowLiveBinding` (`rainbow_live_binding`) : lien (user, actif, wallet) → **wallet réel** (lecture seule) ; l'Affectation jouée est celle de (user, actif) (`affectation` FK, posée à la création). **Unique (`user_id`, `asset_symbol`, `wallet_id`)** (`uk_rainbow_live_binding_user_asset_wallet`) ⇒ un binding par actif **et par wallet**. Une Affectation peut alimenter plusieurs bindings (`findAllByAffectation`). Champs : `wallet` (FK `Wallet`, doit appartenir au user), `bagPercent` (0-100, défaut 100, part **dynamique** de la position réelle offerte à la stratégie), `simulation` (boolean, défaut faux) et `minBuyUsd` (nullable : achat minimum du lien, sous lequel l'achat est reporté en carry), `priority` (ordre de passage du cash, défaut = rang dans `RainbowLiveDefaultPresets.ASSETS` : BTC 0, ETH 1, PAXG 2). **Mode d'exécution** dérivé (`BindingExecutionMode`) : `executionEnabled` ⇒ `ACTIVE`, sinon `simulation` ⇒ `SIMULATION`, sinon `DISABLED` ; `applyExecutionMode` garde les deux booléens exclusifs. Donnée utilisateur créée par l'API, jamais par un initializer. Lu par le moteur via `RealPortfolioSource.read(binding)`. **Retrait = archivage** : `DELETE /api/rainbow-live/bindings/{id}` pose `archived_at` (colonne nullable, créée par `ddl-auto=update`), coupe l'exécution et remet à zéro l'armement / la confirmation du 1ᵉʳ ordre ; la ligne et ses `RainbowLiveBindingRun` restent (historique), mais un lien archivé est ignoré partout (`findByUser…` et la liste admin l'excluent, `owned()` et `arm` répondent 404, onboarding et candidats le traitent comme absent). Relier le même (actif, wallet) **réactive** la ligne archivée (même id, paramètres réinitialisés, exécution coupée, 1ᵉʳ ordre à re-valider). Pas de purge automatique pour l'instant.
- `RainbowLiveRun` (`rainbow_live_run`) : **unique (Affectation, `run_day`)**, `ON DELETE CASCADE` sur l'Affectation ; `user`, `assetSymbol`, `day` (jour UTC), un bloc `@Embedded RainbowLivePassBlock signal` (colonnes `signal_*`), `config` (snapshot) + `configHash`. Signal **par Affectation**, non plafonné.
- `RainbowLivePassBlock` : `close`, `sma`, `atr`, `boundDown2`/`boundDown1`/`boundUp1`/`boundUp2`/`boundUp3` (SMA ± ATR×mult correspondant), `zone`, `athDistance`, `buyFactor`/`sellFactor`, `moonMode`, `buyArmed`/`sellArmed`/`buyLocked`, `cooldownRemaining`, `moonReserveQty`, `activeSet` (nom du preset Rainbow joué) et `trendRegime` (UP/DOWN/RANGE), action décidée (`RainbowLiveAction` BUY/SELL/NONE, `actionAmountUsdc`, `actionQuantity`, `actionPrice`), `configHash`, `computedAt`.
- `RainbowLiveBindingRun` (`rainbow_live_binding_run`) : **unique (binding, `run_day`)**, `ON DELETE CASCADE` sur le binding ; snapshot live **par lien** : un bloc `@Embedded RainbowLiveLiveBlock live` (colonnes `live_*`), `computedAt`.
- `RainbowLiveLiveBlock` : `status` (`PortfolioStatus` OK|UNAVAILABLE|NOT_TRADABLE), `walletId`, `fetchedAt`, `cashUsd`, `cashDetail` (JSON par membre du groupe USD), `positionQty`, `tradableQty`, `cashReserved` (déjà consommé par les actifs servis avant), `blockReason` (`NONE|INSUFFICIENT_CASH|NOT_TRADABLE_WITHOUT_FIAT|UNAVAILABLE`), `actionType` (`BUY|SELL|NONE|BLOCKED`), `actionAmountUsdc`, `actionQuantity`, `candleSource` (exchange réel des candles du signal du lien), `candleSourceSubstituted`.

Suppression d'une Affectation ⇒ runs et états supprimés par FK. Les presets sont référencés, jamais copiés : modifier un preset installé change la config effective de l'Affectation (voir `AffectationConfigResolver`), sans écrire ni recalculer de run.
