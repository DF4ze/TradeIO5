## 1. Décisions à respecter (étude §5-§6)
- Ordres **limit IOC plafonné** (prix plafond = devis ± tolérance slippage 0,05-0,1 %, constante) ; **jamais de market** ; `post_only` non codé en (c).
- Idempotence : `clOrdId` déterministe (celui du plan de (b)) ; **réconciliation avant tout renvoi** (`GET order` par `clOrdId`) ; un timeout/réponse illisible ⇒ étape `UNKNOWN`, jamais de renvoi aveugle.
- Échec partiel : le stock USDT **reste**, aucun retour arrière automatique ; reliquat d'un achat partiel reporté au cycle suivant ; plan `PARTIAL` + alerte.
- Re-devis juste avant chaque étape : arrêt de l'étape suivante si coût rouge (> 0,8 %) ou > coût du plan + 0,05 point ; devis périmé (> TTL 5 min) ⇒ re-devis obligatoire, pas d'exécution sur un vieux plan.
- Sécurités : clé **Trade seulement, jamais Withdraw**, IP VPS allowlistée ; plafonds par ordre (= 1 × `baseAmount` du preset) et par jour/user (= 2 ×) **plus un plafond absolu en constante non surchargeable par la base** ; kill switch lisible sans redéploiement ; mode global `OFF|DRY_RUN|LIVE` (défaut `DRY_RUN`) ; `executionEnabled` par binding (défaut false) ; **double validation du 1ᵉʳ ordre réel d'un binding** (admin arme, puis user confirme) ; qui active : admin arme, user active son propre binding ; impossibilité pour mock/presets non-live d'émettre un ordre ; journal d'audit complet (plan, ordres, réponses sans secret).
- Credentials : `ApiCredential.scope` (`READ|TRADE`), unique (user, provider, scope), **chiffrement au repos AES-GCM**, clé maître en variable d'environnement du VPS (jamais en base, jamais dans Flyway ni le binaire) ; credentials toujours rattachées au `User` ; clés de dev via properties gitignorées poussées en base si absentes (comportement existant de `ApiCredentialInitializer`, étendu au scope).
- Hors lot, à ne pas coder : token natif d'exchange, découverte de wallet, alerte % de liquidité, compte Funding OKX, **retrait/transfert API jamais**, `post_only`, ordre inverse `USDT→USDC`.

## 2. C1 — Back : credentials, port d'ordres, exécuteur, sécurités

### 2.1 Credentials Trade
- `ApiCredential` : champ `scope` (`CredentialScope {READ, TRADE}`, défaut `READ` pour l'existant), contrainte d'unicité (user, provider, scope) à la place de `uk_credential_user_provider` ; migration des lignes existantes (scope = READ) ; `V1__init.sql` Flyway préparé mis à jour ; règle des défauts d'Initializer respectée (`operations/flyway.md`).
- Résolution : un `Wallet` garde sa credential Read pour les lectures ; la credential de trading est **résolue par scope** (user + provider) par un `TradeCredentialResolver`, jamais exposée aux lecteurs de soldes/catalogue ; une credential TRADE absente/désactivée ⇒ pas d'exécution (`CREDENTIAL_INVALID`), jamais d'exception brute.
- `SecretCipher` (AES-GCM, IV aléatoire par valeur, clé maître en variable d'environnement `TRADEIO_MASTER_KEY` ou équivalent) : chiffre `apiKey/secretKey/passphrase` **des credentials TRADE** dès cette étape ; migration prévue pour chiffrer aussi les READ (décision : à proposer à Clem en fin de lot, non obligatoire ici). Absence de clé maître ⇒ le chiffrement TRADE échoue explicitement et l'exécution reste verrouillée ; jamais de repli en clair. Convertisseur JPA (`AttributeConverter`) ou service dédié, `@ToString.Exclude` conservé, aucun secret dans logs/exceptions/DTO.
- Pas de page de saisie en C : création d'une credential TRADE par API admin protégée **uniquement** (la page de saisie des credentials est un chantier séparé, cf. `known-gaps` §5b).

### 2.2 Port d'ordres et client OKX (package dédié, hors `service.connector`)
- Package `service/execution/exchange` : interface `SpotOrderPort` (`submit(OrderRequest) → OrderAck`, `query(clOrdId) → OrderState`, `cancel(clOrdId)`, `fills(clOrdId)`), DTO `OrderRequest/OrderAck/OrderState/Fill` (sans secret). **C'est le seul endroit où des méthodes d'ordre existent.**
- `OkxSpotOrderClient` implémente le port : `POST /api/v5/trade/order` (`tdMode=cash`, `ordType=ioc`, `px`, `sz`, `tgtCcy` selon le côté, `clOrdId`), `GET /api/v5/trade/order`, `POST /api/v5/trade/cancel-order`, `GET /api/v5/trade/fills`. Signature via `OkxSignedRequests` (**réutilisée, pas copiée**) ; erreurs OKX → exceptions typées (rejet métier vs indisponible vs clé rejetée 501xx) ; throttle simple (limites OKX) ; jamais de log du corps signé ni des en-têtes d'authentification. Bean **inactif par défaut** (`@ConditionalOnProperty` sur `tradeio.execution.mode=LIVE` **et** `tradeio.execution.live-unlocked=true`) : sans cela le port n'existe pas dans le contexte.
- `FakeSpotExchange` (test uniquement, `src/test`) : carnet simulé, remplissage total/partiel/nul, rejet, timeout, doublon de `clOrdId`, latence, frais prélevés dans l'actif reçu ; sert à tous les tests du lot.

### 2.3 Exécuteur et machine d'états
- `OrderExecutor` (package `service/execution/run`) : prend un plan `PLANNED` non expiré, vérifie dans l'ordre : mode global, kill switch, `executionEnabled` du binding, `ExecutionGuard` **étendu** (statut `OK` ou `TRADABLE_VIA_BRIDGE` avec chemin calculé — jamais `NOT_TRADABLE_WITHOUT_FIAT`), credential TRADE, double validation du 1ᵉʳ ordre, plafonds (ordre, jour, absolu), TTL. Puis, étape par étape : re-devis → contrôle de dérive du coût → `submit` → attente bornée → `query`/`fills` → mise à jour de l'étape ; l'étape suivante n'utilise que les quantités **réellement reçues** de la précédente.
- États d'étape : `PLANNED → SUBMITTED → FILLED | PARTIAL | REJECTED | CANCELED | UNKNOWN` ; plan : `PLANNED → EXECUTING → EXECUTED | PARTIAL | FAILED`, + `BLOCKED/EXPIRED/CANCELLED`. Transitions **append-only** dans une table d'audit (`rainbow_live_order_event` : plan, étape, type, payload sans secret, `DomainClock`) ; aucune mise à jour destructive de l'historique.
- Réconciliation : au démarrage et avant tout renvoi, toute étape `SUBMITTED/UNKNOWN` est relue par `clOrdId` ; doublon rejeté par l'exchange ⇒ lecture de l'état au lieu d'un échec. Reprise après échec partiel : sans pont compensatoire automatique.
- Fills → `Transaction` (idempotent par `externalTransactionId` = id de fill, frais avec devise : ajouter `feeCurrency` à `Transaction` si absent) ; slippage réel = `fillPx` moyen vs mid au moment du devis, stocké sur l'étape.
- Déclenchement : `ExecutionJob` (cron `tradeio.execution.run-cron`, défaut `-`, `zone="UTC"`) + endpoint admin `POST /api/admin/execution/run?planId=` ; **aucun déclenchement implicite par le bench ou le job de plan**.

### 2.4 Interrupteurs et limites (modèle + API)
- Entité `ExecutionSettings` (une ligne globale) : `killSwitch`, `maxOrderMultiplier`, `maxDayMultiplier` ; plafond absolu en constante `ExecutionDefaults`. `PUT /api/admin/execution/kill-switch` (ADMIN) lisible aussitôt par l'exécuteur (relecture à chaque étape, pas de cache).
- Binding : `executionEnabled` (défaut false), `firstLiveApprovedAt` (posé par l'admin), `firstLiveConfirmedAt` (posé par le user). Endpoints : admin `POST /api/admin/execution/bindings/{id}/arm`, user `PUT /api/rainbow-live/bindings/{id}/execution` (active/désactive) et `POST …/confirm-first-live` ; propriétaire seulement (404 sinon).
- Mode `LIVE` : démarrage refusé tant que `tradeio.execution.live-unlocked` n'est pas vrai **et** qu'une clé maître est configurée (le déverrouillage en production se fait à l'étape d, avec Clem).

### 2.5 Garde-fous d'architecture (obligatoires, aucun assouplissement caché)
- `ConnectorNoOrderMethodTest` : `service.connector.**` reste sans méthode d'ordre (le client d'ordres est dans `service.execution.exchange`). Si le pattern doit évoluer, **le renforcer** (liste blanche explicite d'un seul package), jamais l'affaiblir.
- Nouveau test : (1) seules les classes de `service.execution.exchange` déclarent des méthodes d'ordre ; (2) seules `service.execution.run.*` appellent `SpotOrderPort` ; (3) `service.dca.atr.bench.*` et `service.execution.plan.*` ne dépendent ni du port ni du client ; (4) le bean `OkxSpotOrderClient` est absent du contexte par défaut ; (5) mode `LIVE` sans déverrouillage ou sans clé maître ⇒ échec au démarrage ; (6) `RainbowLiveNoExchangeDependencyTest` inchangé et vert.
