## 1. Décisions à respecter (étude §2 et §4)
- Hiérarchie : Stratégie (aujourd'hui `RainbowLivePreset.mode`) → Preset (porte l'actif) → Lien. **Pas de nouvelle entité « Stratégie ».**
- Lien = `(user, provider/wallet, actif)` unique ; le **preset est un attribut hors unicité** ; **un même preset peut alimenter plusieurs liens** (la règle « un preset = un seul binding » ajoutée à l'étape intermédiaire est à retirer).
- **Simulation partagée par preset, live par lien** : l'état moteur (`RainbowLiveEngineState`), le wallet fictif (`RainbowLiveMockWallet`), les événements de preset et le run de simulation restent par preset. Tout ce qui dépend du wallet réel (cash, position, `bagPercent`, action live plafonnée, réservation de cash, snapshot) devient **par lien**.
- Garder le terme « binding » dans le code, l'API et l'UI (le nom du lien n'est pas choisi) ; **aucun renommage** dans ce lot.
- Ne rien durcir : un KO de tradabilité continue d'être enregistré et affiché (pas de refus de création). Le preset de l'actif demandé reste obligatoire (400 sinon, comme aujourd'hui).
- Pas de Flyway activé : `ddl-auto=update` + SQL manuel documenté dans `operations/flyway.md` ; `V1__init.sql` régénéré (`FlywaySchemaTest -Dflyway.generate=true` puis `-Dflyway.check=true`).
- Ne casse rien : API, JS et tests existants doivent rester valides sauf là où ce prompt dit de les changer.
