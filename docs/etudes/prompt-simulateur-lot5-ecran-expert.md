## Constat à intégrer (vérifié le 2026-11-15, à re-vérifier)
Le rejeu du lot 1-4 (`FullReplayService#setup` / `loadLink`) est **bâti pour la parité** : période = 1er au dernier `RainbowLiveBindingRun`, position initiale = snapshot live, cours de décision = `actionPrice` 23:55 des `RainbowLiveRun`, ATH = `rainbow_ath_reference` stocké, réglages de modulation = journal live, ré-amorçage après trou de passes. Un simulateur utilisateur sur **plage libre** ne peut pas en dépendre (pas de run live avant l'ouverture du lien, ni sur 24 mois). Il faut donc **un second constructeur de rejeu, libre** :
- période = plage demandée (défaut 24 derniers mois, comme les autres simulations), bougies D1 du lien via `DailyDataLoader` / `MarketDatasetEngine#getDailyDatasetForAsset` (source du lien, `substituted` ⇒ erreur explicite, pas de fallback) ;
- cours de décision = clôture D1 du jour (le 23:55 n'existe pas dans l'historique) — à noter dans le résultat comme écart assumé vs la prod ;
- ATH et automate moon calculés sur tout l'historique chargé, démarrage à froid en début de plage (comme `SimulationEngine`), sans `athBefore` ni `rebootstrapDays` ;
- réglages de modulation = réglages effectifs de l'utilisateur (`UserTradingSettingsService#effectiveSettings`) + surcharges de la demande, constants sur toute la plage ;
- capital de départ = `cash0` de la demande (défaut : valeur du wallet réel à l'instant du lancement), position initiale de départ = 0 par défaut (tout en USDC ; à valider) ;
- liens : `RainbowLiveBinding` du wallet de l'utilisateur (priorité, bag, montant de base, affectation → Trend + jeux Bull/Bear via `RainbowLiveTrendConfigs`), surcharges par lien, liens inactifs écartés.
**Une seule implémentation** : réutiliser `MultiLinkReplayEngine`, `LinkSignalReplay`, `EpisodeTimeline`, `OrderReplay` / `ReplayScheduleBuilder` ; factoriser avec `FullReplayService#loadLink` plutôt que dupliquer (extraire la résolution Trend / jeux / bornes). La parité garde son chemin et ses tests inchangés.
